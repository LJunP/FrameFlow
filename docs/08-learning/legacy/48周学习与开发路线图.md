# 1. 先读：边界、原则与成功标准

## 1.1 这个项目能证明什么，不能证明什么？

完成本路线后，你可以用代码、测试、部署、压测、监控和故障复盘证明：

- 你能独立分析并实现中小型企业后端业务；
- 你理解并实践了主流 Java 后端技术；
- 你可以在隔离环境中部署、监控、定位常见故障；
- 你知道每个技术解决什么问题，也知道其限制和替代方案。

它**不能**自动等同于：

- 大规模生产系统的多年经验；
- 真实百万用户、跨地域、多机房运维经验；
- 7×24 值班经验；
- 团队协作、合规审计、真实商业成本控制经验。

面试时必须真实表述：

> 我独立设计并完成了一个面向视频创作团队的学习型/试用型项目，在本地和测试环境完成了相关工程实践、压测和故障演练。

不要说“我在线上生产环境处理过事故”，除非事实确实如此。

## 1.2 总学习闭环：任何技术都按这 8 步走

不要先背完技术，再做项目。每增加一个技术，必须完成：

```text
业务问题
  → 最小原理
  → 最小实现
  → 自动化测试
  → 边界与故障实验
  → 日志/指标/链路观察
  → 修复与复盘
  → 2 分钟口述解释
```

例如 RabbitMQ：

```text
问题：素材上传后，AI 转写可能耗时 3 分钟，不能阻塞上传接口。
原理：生产者把任务发送给队列；消费者异步处理；确认机制保证消息不轻易丢失。
实现：上传成功后发送“素材分析任务”。
测试：发送成功、消费成功、处理失败、重复消费。
故障：关闭消费者、模拟 AI 超时、制造错误消息。
观察：队列长度、失败次数、重试次数、处理时延。
复盘：为什么要 ACK？为什么需要死信队列？
表达：能说明 RabbitMQ 用于“待执行任务”，Kafka 用于“已发生事件”。
```

## 1.3 AI 的正确角色

AI 可以是：

- 解释概念的老师；
- 评审需求和架构的助手；
- 审查代码的 reviewer；
- 生成测试用例清单的测试助手；
- 协助阅读日志和提出排查假设的助手；
- 模拟面试官。

AI **不是**：

- 不经理解直接复制全部代码的代写工具；
- 未经验证就可信的架构决策者；
- 可以接收真实密码、Token、客户数据、个人信息的外部系统；
- 可以替你进行最终测试和上线判断的责任人。

每次采用 AI 代码前都要：

```text
1. 自己读懂每一段；
2. 自己运行；
3. 写或补测试；
4. 主动修改一个需求验证自己理解；
5. 写下“为什么这样设计”。
```

## 1.4 你的四级能力标准

| 等级 | 标准 |
|---|---|
| 知道 | 能说清它解决什么问题、核心概念是什么。 |

| 可面试证明 | 有业务代码、测试、指标或故障复盘，能经得起追问。 |

目标岗位中，建议目标等级：

| 技术 | 目标等级 |
|---|---|
| Java、Spring Boot、MySQL | 熟练 / 可面试证明 |
| Redis、RabbitMQ、Docker | 熟练 / 可面试证明 |

# 2. 项目定位、用户与业务闭环

## 2.1 项目一句话定义

**FrameFlow** 是一个面向 **3～30 人视频创作团队、摄影工作室、小型品牌内容部门** 的 AI 视频项目协同与交付平台。

它解决的不是“AI 一键生成视频”，而是视频商业项目中更常见的协作混乱：Brief 分散、素材和版本混乱、审片意见无法定位、授权到期遗漏、交付不可追溯、异步处理难管理。

## 2.2 目标用户与痛点

| 用户 | 核心痛点 | 首期解决方式 |
|---|---|---|
| 制片 / 项目经理 | Brief、进度、负责人分散 | 项目、Brief、任务、状态管理 |
| 摄影 / 剪辑 | 素材版本难找、修改要求混乱 | 素材版本、任务、时间点批注 |
| 客户 | 不知道目前交付到哪、反馈散落 | 审核链接、批注、确认状态 |
| 团队负责人 | 不知道项目是否逾期、授权是否到期 | 项目看板、提醒、审计记录 |
| 内容团队 | 素材转写和标签耗时 | RabbitMQ 异步 AI 分析任务 |

## 2.3 MVP：第一版只做这些

```text
用户、团队、成员角色
→ 客户、项目、Brief 版本
→ 分镜/任务及负责人
→ 素材上传、素材版本、标签
→ 审片/时间点批注/审核状态
→ 交付记录
→ AI 摘要、分镜草稿、素材标签（仅辅助）
```

## 2.4 明确不做的内容

至少在 MVP 前，不做：

```text
自研视频剪辑器
自研视频转码引擎
自研大模型或视频生成模型
支付与复杂财务结算
移动端 App
直播系统
社交社区
几十个微服务
复杂炫酷前端
```

## 2.5 核心业务闭环

```text
团队成员接收客户 Brief
  → 创建视频项目
  → 维护 Brief 版本
  → 拆分分镜和制作任务
  → 上传素材并创建版本
  → 异步 AI 分析（标签/摘要/转写）
  → 团队与客户进行时间点批注
  → 提交审核
  → 修改后形成新版本
  → 客户确认交付版本
  → 归档交付物、记录授权与复盘数据
```

## 2.6 核心实体（先理解，不急着全建）

```text
User                用户
Team                团队
TeamMember          团队成员与角色
Client              客户
VideoProject        视频项目
Brief               需求 Brief
BriefVersion         Brief 版本
ShotTask            分镜/镜头任务
Asset               素材（逻辑资产）
AssetVersion        素材版本
Review              审核单
ReviewComment       时间点批注
Delivery            交付记录
License             授权规则
AiTask              AI 分析任务
OutboxEvent         可靠事件表
```

## 2.7 状态机：先写规则，再写代码

### 项目状态

```text
DRAFT（草稿）
→ PLANNING（策划）
→ SHOOTING（拍摄）
→ EDITING（制作）
→ REVIEWING（审核）
→ DELIVERED（已交付）
→ ARCHIVED（已归档）
```

规则示例：

- `DELIVERED` 项目不能直接删除；
- `ARCHIVED` 项目默认只读；
- 非项目成员不能改变项目状态；
- 客户只能触发“确认”或“要求修改”，不能直接更改内部制作任务。

### 审核状态

```text
PENDING_REVIEW（待审核）
→ CHANGES_REQUESTED（需修改）
→ APPROVED（已通过）
→ REJECTED（已拒绝）
```

### 素材版本状态

```text
UPLOADED（已上传）
→ ANALYZING（分析中）
→ READY（可用）
→ IN_REVIEW（审核中）
→ LOCKED_FOR_DELIVERY（交付锁定）
→ ARCHIVED（归档）
```

# 3. 技术地图：每项技术为什么存在

> 任何技术都必须先回答：“不用它会有什么具体问题？”

| 技术 | 在 FrameFlow 中解决的真实问题 | 第一处落地 |
|---|---|---|
| Java 集合/泛型/异常 | 组装任务、权限、标签和批处理结果 | 任务列表、标签聚合 |
| Java 并发/线程池 | 批量通知、文件处理、异步任务隔离 | AI 任务或批量导入 |
| Spring Boot | REST API、依赖注入、校验、配置、事务 | 单体 MVP |
| MySQL | 用户、团队、项目、任务等稳定关系型业务 | 第 1 阶段 |
| Redis | 高频读取缓存、幂等、限流、短期状态 | 项目详情缓存 |
| MinIO | 大文件、素材、封面、交付包存储 | 素材上传 |
| RabbitMQ | 需要可靠执行的耗时任务 | AI 分析、通知、重试 |
| DDD | 素材版本/授权/交付的复杂规则封装 | 素材授权领域 |
| PostgreSQL | JSONB 元数据、审计事件、复杂版本查询 | 素材/授权子域 |
| Kafka | 多服务订阅“已经发生”的领域事件 | 交付/审核事件 |
| Outbox | 数据库写成功但消息发送失败的一致性问题 | 版本创建、交付事件 |
| Spring Cloud/Nacos | 多服务注册、发现、配置管理 | 微服务阶段 |
| Gateway/Feign | 统一入口、服务调用、鉴权与路由 | 微服务阶段 |
| Sentinel/Resilience4j | AI 或下游服务慢/挂时保护核心业务 | AI 服务调用 |
| OpenTelemetry | 跨服务、消息队列追踪同一次请求 | Cloud 阶段 |
| Prometheus/Grafana | 观察延迟、错误、队列堆积、资源使用 | 可观测性阶段 |
| Docker | 固化运行环境 | 单体打包后 |
| Kubernetes | 服务部署、扩容、回滚、健康检查 | Cloud 完成后 |
| Istio | 灰度发布、流量治理、mTLS、AuthorizationPolicy | M16-G 受限实验 |

# 4. 每日、每周与每个功能的固定工作法

## 4.1 每日 5 小时模板

| 时段 | 做什么 | 必须产出 |
|---|---|---|
| 1 小时 | 学当天必要概念 | 一页笔记 + 5 个自测问题 |
| 30 分钟 | 写业务规则、接口、表或流程图 | 设计草稿 |
| 2 小时 | 自己实现最小功能 | 可编译、可运行代码 |
| 1 小时 | 调试、写测试、修复问题 | 测试记录或 Bug 记录 |
| 30 分钟 | 复盘、Git 提交、AI 追问 | 日报 + 提交 |

> 如果当天遇到 Bug 超过 1 小时：停止无目的改代码，记录现象、日志、已尝试方案；再向 AI 或资料提问。

## 4.2 每周 6 天模板

| 日期 | 重点 |
|---|---|
| Day 1 | 学概念 + 业务规则 + 数据模型 |
| Day 2 | 最小接口/最小实现 |
| Day 3 | 完善核心逻辑 |
| Day 4 | 边界、权限、异常处理 |
| Day 5 | 单元/集成测试、修复 |
| Day 6 | 文档、演示、复盘、补漏、模拟面试 |
| Day 7 | 休息；或仅 1 小时回顾，不加新功能 |

## 4.3 每个功能的开发卡

在开发任何功能前，先在 `docs/00-product/` 写一张卡：

```markdown
# 功能：素材版本创建

## 谁在什么场景使用？
## 用户要完成什么？
## 输入、输出和成功标准？
## 业务规则？
## 权限规则？
## 异常场景？
## 并发场景？
## 需要哪些表/字段/索引？
## 是否需要事务？
## 是否需要缓存或消息队列？为什么？
## 测试用例？
## 指标和日志？
```

完成后补充：

```markdown
## 实际实现与设计差异
## 遇到的 Bug
## 根因
## 修复方案
## 下次如何预防
## 2 分钟项目讲解稿
```

## 4.4 “学习一个知识点”必须做什么？

以 `@Transactional` 为例，不是只看定义。你必须：

1. 说明什么是事务、ACID 各是什么；
2. 说明本项目哪两个数据库操作必须一起成功；
3. 写一个“素材版本创建 + 审计记录”业务；
4. 故意让第二步抛异常；
5. 验证第一步是否回滚；
6. 理解哪些场景不生效（自调用、异常类型、异步线程等）；
7. 写测试；
8. 用自己的话解释事务边界为什么在 Service，而不在 Controller。

## 5.3 Git 规范

分支：

```text
main                可演示、可运行
feature/<topic>     一个功能或专题
fix/<issue>         修 Bug
```

提交格式：

```text
feat: add project creation API
feat: add asset analysis retry queue
fix: prevent duplicate delivery confirmation
test: add asset version service tests
docs: document review workflow
ops: deploy asset service to kind
refactor: isolate delivery domain service
```

每次提交前检查：

```text
代码能编译？
测试通过？
没有提交密码、Token、.env？
没有提交 target/、日志、大文件？
提交说明能看懂？
```

## 5.4 安全红线

- 不把数据库密码、API Key、Webhook、JWT 密钥写入 Git；
- 使用 `.env.example` 或 `application-local.example.yml` 示例文件；
- 真实用户数据、客户 Brief、视频素材不要发给外部 AI；
- 不使用当前项目已有的真实配置作为练习环境；
- 不直接运行当前项目会调用外部 CPS、Kafka、Webhook、数据库写操作的测试；
- 学习阶段所有中间件都使用本地 Docker Compose 的隔离环境。

# 6. 48 周逐周执行计划

> 每周都执行：**学习 → 设计 → 编码 → 测试 → 复盘 → Git 提交**。  
> “资料方向”优先级：官方文档 > 权威教程 > AI 解释 > 博客。AI 给出结论后，至少再对照一次官方文档或实际实验。

## 阶段 A：工具、Java、Git、SQL（第 1～4 周）

### 第 1 周：开发环境、Git、Java 语法

**本周目标**：能独立创建 Java 项目、运行程序、用 Git 保存过程。

**必须学习**：

- 终端：`pwd`、`ls`、`cd`、创建/删除目录的概念；
- Java：变量、基本类型、字符串、条件、循环、方法、类、对象、访问修饰符；
- 异常：`try/catch/finally`；
- Git：仓库、工作区、暂存区、提交、分支概念；
- Maven：`pom.xml`、依赖、`mvn test`、`mvn package` 是什么。

**练习**：

1. 写 `VideoProject`、`TeamMember`、`Task` 三个普通 Java 类；
2. 写一个命令行程序，可创建、查看、删除项目；
3. 用 `List<VideoProject>` 保存项目；
4. 用 `Map<Long, VideoProject>` 根据 ID 查询项目；
5. 对错误输入抛出并捕获异常；
6. 创建 Git 仓库，完成至少 10 次小提交。

**自测问题**：

- `List` 与 `Map` 的区别？
- 一个对象和一个类的区别？
- 为什么异常不能直接忽略？
- `git add` 与 `git commit` 分别做什么？
- Maven 为什么需要 `pom.xml`？

**验收**：不看教程，能重新写出命令行项目管理程序，并解释每个类的职责。

**AI 提问模板**：

```text
我是 Java 初学者。请不要给我完整项目代码。
请以“视频项目管理命令行程序”为例解释 List、Map、类、对象、异常分别解决什么问题。
先讲概念，再给我 3 个小练习和 5 个检查问题。
```

## 阶段 C：Redis、MinIO、RabbitMQ、AI 与 MVP（第 13～20 周）

### 第 14 周：Redis 幂等、限流与分布式锁入门

**业务问题**：客户可能重复点击“确认交付”；高频接口可能被误用或攻击。

**必须学习**：

- 幂等的定义；
- 幂等 key；
- 原子 `SET NX EX`；
- 令牌桶/固定窗口概念；
- 分布式锁的风险和适用边界。

**开发**：

- 交付确认接口使用 Idempotency-Key；
- 对 AI 提交接口做基础限流；
- 先实现简单 Redis 原子操作，后续再学习 Redisson。

**测试**：并发发 20 个相同确认请求，确保只有一个实际完成。

### 第 17 周：RabbitMQ 可靠消费、重试与死信

**开发**：

### 第 25 周：Kafka 基础与领域事件

# 7. 技术专项学习卡片

## 7.1 Java 集合、并发与 JVM

**先学**：List/Set/Map、HashMap、ConcurrentHashMap、泛型、Stream、异常；线程、线程池、Runnable/Callable、Future/CompletableFuture、volatile、synchronized、锁、JMM；堆/栈/GC/类加载。

**项目落点**：标签去重、批量任务分片、权限集合、AI 批量处理、线程池隔离。

**最小实操**：使用有界 `ThreadPoolExecutor` 执行批量通知；显示队列长度、活跃线程数、拒绝次数。

**故障实验**：队列堆积、拒绝策略触发、死锁、内存增长。

**熟练标准**：能说明 CPU 密集/IO 密集线程池差异，为什么阻塞任务不应默认使用 common pool，如何用 jstack/JFR 定位。

**AI 提问**：

```text
请以 FrameFlow 的“批量 AI 分析任务”为例，解释线程池核心数、最大线程数、队列、拒绝策略如何选择。
不要只给参数；请给出负载假设、风险、监控指标和一个故障实验。
```

## 7.2 Spring Boot

**先学**：Bean 生命周期基础、IoC/DI、MVC、配置、Profile、Validation、AOP、事务、异常处理、测试。

**最小实操**：创建项目接口：参数校验 → Service 业务规则 → Mapper 持久化 → 统一响应。

**故障实验**：校验失败、业务异常、数据库异常、事务回滚。

**熟练标准**：能解释 DTO/Entity/VO、AOP 使用边界、事务不生效常见原因。

## 7.3 MySQL

**先学**：数据建模、索引、事务隔离、锁、执行计划、慢 SQL、连接池。

**项目落点**：用户、团队、项目、任务等关系型稳定业务。

**最小实操**：项目列表筛选/分页；创建联合索引；用 EXPLAIN 对比优化前后。

**故障实验**：无索引慢查询、连接池耗尽、重复提交。

**熟练标准**：能解释索引选择、覆盖索引、事务边界和慢 SQL 排查过程。

## 7.4 PostgreSQL

**先学**：JSONB、GIN、CTE、窗口函数、UPSERT、MVCC、EXPLAIN ANALYZE。

**项目落点**：素材结构化元数据、授权快照、AI 返回结构、审计事件。

**最小实操**：JSONB 查询 + GIN 索引；窗口函数查素材最新版本。

**熟练标准**：能解释为什么这里选 PostgreSQL，为什么 JSONB 不取代所有关系型建模。

## 7.5 Redis

**先学**：数据结构、TTL、缓存旁路、序列化、穿透/击穿/雪崩、原子操作、限流、锁。

**项目落点**：项目详情、权限缓存、确认交付幂等、AI 接口限流。

**故障实验**：缓存过期、Redis 下线、热点 key、并发重建缓存。

**熟练标准**：能讲清缓存一致性取舍、Key 命名、何时不用锁。

## 7.6 RabbitMQ

**先学**：Exchange/Queue/Binding、ACK/NACK、Confirm、TTL、DLX、重试、幂等、积压。

**项目落点**：素材 AI 分析、通知、延迟提醒。

**故障实验**：消费者宕机、AI 超时、毒消息、重复消费、队列堆积。

7. Redis：`config/RedisConfig.java` → `resources/lua/rate_limit.lua` → `common/RedisRateLimiter.java` → `config/RedissonRateLimiter.java`；
8. Kafka：`kafka/KafkaProducerService.java` → `yc-consume-api/.../MediaOrderConsume.java`；

## 8.2 从它学习什么，不学习什么？

| 可学习 | 需要批判性看待 |
|---|---|
| Maven 多模块、Controller-Service-Mapper 分层 | 不把传统三层架构误认为 DDD |
| MyBatis-Plus、Mapper XML、多数据源 | 不复制真实内网连接与明文凭据 |
| Redis 配置、Lua 限流、Redisson | 不在真实 Redis 上做删除/限流实验 |
| Kafka Producer/Consumer、回调、重试 | 关注自动提交 + subscribe 带来的可靠性风险 |
| AOP 日志、MDC、JSON 日志 | 审查请求/响应日志中的敏感信息 |
| Docker/Jenkins 思路 | 不直接运行会停止容器、远程 SSH 发布的流水线 |
