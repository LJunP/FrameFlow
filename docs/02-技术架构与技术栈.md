# 02 · 技术架构与技术栈

> FrameFlow Select 唯一的技术事实源。选型理由与边界以本文档为准；
> 产品语义见《01-产品与领域设计》，开发顺序见《03-开发与学习路线》。

## 1. 总体架构

```text
                    ┌─────────────────────────────┐
                    │   frameflow-web (Next.js)   │  轻前端：登录/批次/审阅/导出
                    └──────────────┬──────────────┘
                                   │ REST (JSON, JWT)
                    ┌──────────────▼──────────────┐
        ┌────────── │  frameflow-app (Java 17)    │ ──────────┐
        │           │  Spring Boot 模块化单体      │            │
        │           │  identity │ product 模块     │            │
        │           └──┬─────────┬─────────┬──────┘            │
        │              │         │         │                    │
   ┌────▼────┐   ┌─────▼───┐ ┌───▼─────┐ ┌▼──────────┐   ┌─────▼─────┐
   │PostgreSQL│   │ RabbitMQ│ │  Redis  │ │   MinIO   │   │ frameflow │
   │  16      │   │ 任务队列 │ │ 缓存/限流│ │ 对象存储  │   │ -ai-worker│
   │ 唯一事实源│   └─────┬───┘ └─────────┘ └───────────┘   │ (Python)  │
   └──────────┘         │    ▲                          └─────┬──────┘
                        ▼    │ 结果幂等回写                     │
                  ┌──────────┴─────────┐                       │
                  │ worker 消费分析任务  │◄──────────────────────┘
                  └────────────────────┘
```

**形态：模块化单体（Modular Monolith）+ 异步 Python Worker + 轻前端。**
后端为主、前端为轻；MVP 阶段明确不拆微服务。

## 3. 后端模块边界

```text
frameflow-app
├── identity   用户、团队、成员、角色、JWT 签发与刷新、请求幂等
└── product    Project / Profile / Batch / Candidate / Analysis / Ranking / Selection
```

规则：

1. identity 与 product 模块边界清晰，跨模块只走公开接口，不直连对方表；
2. OpenAPI 契约是唯一 API 权威，契约差异测试保证运行时与文档一致；
3. Worker（Python）不直接写业务库，结果通过回写接口幂等入库。

## 4. 关键技术决策

### 4.1 PostgreSQL 是唯一事实源

所有业务状态、版本化配置、Evidence 记录只在 PostgreSQL 中落库。
字节（视频文件）在 MinIO，元数据在 PG，两者分离、互相引用。

### 4.2 异步分析与可靠性

分析天然耗时，必须异步：批次调度 → RabbitMQ 任务 → Python worker 消费 →
结果幂等回写。要求：Publisher Confirm、消费者 ACK、失败重试有上限、
超限进 DLQ 且可重放、任务与结果幂等（同一候选同一 run 不产生重复结论）。

### 4.3 Redis 只做可丢失的事

限流、热点缓存、批次进度缓存、Cache-Aside。永远可丢失、可重建，
宕机时业务降级但不不可用；严禁把业务事实只存在 Redis。
必须实践：TTL 与失效、缓存穿透/击穿防护、宕机降级实验。

### 4.4 RabbitMQ 而非 Kafka

任务分发型场景，需要 ACK/路由/DLQ，单团队规模下 Kafka 是过度设计。
（若未来有真实事件流需求，须有测量证据再评估。）

### 4.5 对象存储用法

Presigned URL 直传、Multipart Upload 分片、对象版本、生命周期规则。
数据库只存 bucket/key/版本/校验和，不存文件本身。

### 4.6 AI 输出只是建议；模型由平台托管、用户按白名单选择

任何模型结论都必须带 Evidence 束，只进人工复核，不自动淘汰候选。
Provider 全部走 Adapter 接口，可替换、可 Mock；只有显式测试配置才允许 Fake。
无 Key、端点故障或响应损坏时，语义调用转成 `ERROR` Finding 并进入人工复核，
不能伪装成模型已完成判断，也不能让整条确定性分析任务失败。

多模型目录通过同一个无密钥 JSON 契约下发给 Java API 与 Python Worker：

```json
{
  "defaultModelId": "balanced-v1",
  "models": [{
    "id": "balanced-v1",
    "label": "均衡模型",
    "description": "平台推荐的日常复核模型",
    "provider": "openai-compat",
    "model": "vendor-vision-model",
    "baseUrl": "https://provider.example/v1",
    "apiKeyEnv": "FRAMEFLOW_MODEL_BALANCED_V1_API_KEY",
    "enabled": true
  }]
}
```

- Java 只向已登录用户投影 `id/label/description/provider/model/enabled`，不返回
  `baseUrl`、`apiKeyEnv` 或 Key；Profile 发布时校验白名单，并把省略的默认
  `modelId` 固化进版本快照；
- Worker 根据同一 `modelId` 解析私有路由，再从 `apiKeyEnv` 指向的 Worker
  环境变量读取凭据。未知/停用选择不回退；
- 目录的逻辑 ID 是审计版本，不是可随意修改的展示别名。换实际模型必须发新 ID；
- 未配置目录时仅为已有部署合成 `platform-default` 兼容项，继续读取旧的
  `FRAMEFLOW_SEMANTIC_BASE_URL/API_KEY/MODEL`，不影响已发布 Profile；
- Evidence 记录逻辑 `modelId` 和实际 `model`，但永不记录路由地址与凭据。

### 4.7 明确不引入（除非有真实测量证据）

Kubernetes、Istio、Kafka、微服务拆分、Service Mesh、大型向量数据库集群。
"公司都在用"不构成引入理由，必须有本项目的真实瓶颈数据。

## 5. 环境与部署拓扑

四套逻辑隔离环境：**local（本机）→ dev（非生产 VPS）→ staging（类生产）→
production（独立生产 VPS）**。隔离要求：数据库、Redis、RabbitMQ VHost、
MinIO Bucket、Docker Network/Volume、环境变量、Secret、域名、日志、备份
全部按环境隔离，禁止跨环境共用生产数据。

- 默认拓扑 2 台 VPS：1 台跑 dev + staging（逻辑隔离）+ 1 台独立 production；
- 晋级原则：**Build once, promote the same image**——同一镜像以
  Git SHA + 语义版本 + 不可变 Digest 三重标识沿 dev → staging → production 晋级；
- Production 发布必须人工审批；Production 所在环境必须有监控、备份与恢复演练；
- 入口：Nginx + HTTPS（证书自动续期）+ 域名 DNS。

详见 `infra/` 各环境目录说明。

## 6. CI/CD

GitHub Actions：PR 触发 → Java verify（含 Testcontainers）→ Python pytest →
Web build → 构建镜像推 Registry → dev 自动部署 → Smoke Test；
staging / production 晋级为手动门禁。

## 7. 测试策略

| 类型 | 要求 |
| --- | --- |
| 单元测试 | 领域逻辑、状态机、评分算法 |
| 集成测试 | Testcontainers 起 PG/RabbitMQ/MinIO，覆盖上传→分析→回写闭环 |
| 契约测试 | OpenAPI 与运行时行为一致 |
| 越权负例 | 每个接口至少一条 401/403/404 用例 |
| 幂等测试 | 重复回写、重复请求不产生重复数据 |
| 恢复测试 | DB 恢复、消息重放、对象存储恢复 |
| worker 测试 | pytest + 可再生成的合成媒体 fixture |
