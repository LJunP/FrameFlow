# 03 · 开发与学习路线（功能驱动）

> 本项目最终要同时达成两件事：**把产品做出来** + **掌握做它所需的全部技术**。
> 开发模式：**Agent 实现全部代码并标注核心注释，所有者通过阅读源码学习**。
> 产品语义见《01》，技术选型见《02》。状态记录在 `.learning/PROGRESS.md`。

## 0. 协作模式与推进方式

### 0.1 分工

- **Agent（开发方）**：实现每个功能的全部代码、测试与部署配置；遵守 0.2 的
  注释规范；为每个功能产出一份《源码导读》（0.3）。
- **所有者（学习方 + 决策方）**：按导读阅读源码、本地运行验证、向 Agent 提问；
  在 PROGRESS.md 维护自己的学习状态；项目方向、功能验收、发布审批只由所有者
  拍板。
- **物理动作例外**：服务器购买、SSH 登录操作、DNS 配置、生产发布审批等只能
  由所有者亲手执行；Agent 准备全部配置与脚本，并给出逐步操作指引（F9 起）。

### 0.2 代码注释规范（Agent 强制遵守）

1. **核心逻辑必须标注**：状态机迁移、事务边界、幂等设计、安全控制、并发与
   可靠性、关键算法，用 `// ★ 核心：` 前缀注释，写清三件事——
   **做什么、为什么这样设计、改坏会发生什么**。
2. **调用链入口标注阅读顺序**：每个功能的入口文件（Controller / 配置类 /
   main）注释里写明"本功能从哪个文件开始读、按什么顺序读"。
3. **不刷注释**：样板代码、getter/setter、纯配置项不加废话注释，保持信噪比。
4. 注释解释"为什么"，不复述"是什么"——代码本身能表达的不重复写。

### 0.3 每个功能的交付三件套

1. **代码与测试**：`./mvnw -B -q verify`（及对应 worker/web 校验）全绿；
2. **《源码导读》**：`docs/guides/F<n>-源码导读.md`，包含——
   - 阅读地图：按顺序列出本功能该读的文件/类，每个一句话说明；
   - 核心代码索引：★ 标注所在文件:行号 与讲解；
   - 本功能涉及技术点的集中讲解（为什么选这个方案、备选是什么）；
   - 运行与验证方法（怎么本地跑起来、怎么亲眼看到效果）；
3. **自测问题**：所有者读完导读和源码后，能不看资料回答即算理解通过。

### 0.4 推进纪律

1. **一次只做一个功能**。功能内任务按 T1、T2… 编号，做完在 PROGRESS.md 更新。
2. Git 流程：每个功能开 `feature/f<n>-<短名>` 分支，完成后合回
   `frameflow-select/learning-main`；conventional commits（feat/fix/test/docs/chore）。
3. 学习状态由所有者本人在 PROGRESS.md 维护（`未读 / 阅读中 / 已理解`），
   **Agent 不得代标"已理解"**。
4. 红线（永久有效）：
   - 不 push 远端、不改写历史、不动 `.git`；不向冻结分支提交
   - 不通过改测试/阈值/历史迁移制造 PASS；同一实现策略最多试两次，第二次失败
     必须写根因分析
   - `ANALYSIS_ERROR` 严禁伪装成视频不合格
   - 答案册分支（`archive/frameflow-select-agent-mvp-v1`）可作架构参考，但必须
     按当前文档与 JDK 17 基线重新实现，不得直接搬移旧代码充当新实现
   - `PROJECT_COMPLETE` / `PILOT_VALUE_PROVEN` 只能由所有者依据数据批准

## F1 · 工程基线与用户认证

**目标**：建立工程基线；产品能注册、登录、携带 JWT 访问受保护接口。

**必学技术点**：Git 分支/合并/回滚流程；Maven 多模块与生命周期；
Spring Boot 启动与自动配置；REST 接口与 Bean Validation；Spring Security +
JWT（RS256 签发/刷新/过期）；Flyway 首批迁移（用户/团队/成员表）；
PostgreSQL 接入；JUnit 单测 + @SpringBootTest 集成测试 + Testcontainers。

**任务分解**：
- T1 `GET /api/v1/ping`（返回版本与时间）+ 自定义配置读取 + 单测/集成测试，
  走完整 feature 分支流程；
- T2 用户/团队/成员表设计与 Flyway 迁移；
- T3 注册/登录/刷新 Token 接口（密码哈希、RS256、短时效）；
- T4 受保护资源示例接口 + 401/403 越权负例测试；
- T5 请求幂等记录表与中间件。

**完成标准**：ping 与认证接口 curl 可用；错误返回统一错误模型；
verify 全绿含越权负例；导读能讲清 Spring Boot 启动流程与 JWT 链路。

**自测问题**：JWT 与 Session 的取舍？RS256 与 HS256 区别？Flyway 为什么只前向？
@Testcontainers 解决了什么问题？

**目标**：创建 Generation Batch，批量上传候选视频，字节进 MinIO、元数据进 PG。

**必学技术点**：MinIO/S3 API；Presigned URL 直传；Multipart 分片上传与断点；

**任务分解**：

**完成标准**：单文件与分片上传均可回放验证；坏文件进 INVALID 且证据留痕；

**自测问题**：为什么 Presigned 直传而不是走后端中转？分片上传如何保证完整性？

## F4 · 确定性质检流水线

**目标**：批次触发分析 → RabbitMQ 派发 → Python worker 执行确定性检测 →
结果幂等回写，产出带证据的 Finding。

**必学技术点**：RabbitMQ（ACK、Publisher Confirm、重试上限、DLQ、死信重放）；
批次调度与背压；Python 工程化（打包、配置、日志、pytest）；ffprobe/OpenCV
检测器（黑帧/冻结/静音/时长/分辨率/帧率）；幂等回写；ANALYSIS_ERROR 语义。

**任务分解**：
- T1 Analysis Run 状态机 + 批次调度（并发与上限）；
- T2 RabbitMQ 派发与消费骨架（Confirm/ACK/重试/DLQ）；
- T3 Python worker：任务拉取 + ffprobe 元数据核验检测器；
- T4 黑帧/冻结/静音检测器（OpenCV）+ pytest 用例；
- T5 结果幂等回写接口（重复回放不产生重复 Finding）；
- T6 DLQ 重放工具与积压告警。

**完成标准**：上传→分析→Finding 全链路 E2E 测试通过；杀掉 worker 中途恢复
不丢任务不重复结论；坏视频进 ANALYSIS_ERROR 而非 AUTO_REJECT；DLQ 可重放。

**自测问题**：消息丢失/重复/乱序各自如何防？幂等键怎么设计？
背压在批次场景为什么必要？

## F5 · 缓存与限流（Redis）

**目标**：给热点路径加缓存与限流：登录限流、批次进度缓存、项目列表缓存。

**必学技术点**：Redis 数据结构与 TTL；Cache-Aside 与一致性；缓存穿透/击穿/雪崩
防护；限流算法（固定窗口/令牌桶）；宕机降级（Redis 挂了业务仍可用）。

**任务分解**：
- T1 登录接口限流（令牌桶）；
- T2 批次进度查询缓存（Cache-Aside + 短 TTL + 失效广播）；
- T3 穿透/击穿防护（空值缓存/互斥重建）；
- T4 Redis 宕机降级演练（记录降级路径与恢复）。

**完成标准**：限流与缓存各有正反测试；演练有记录；导读能解释每种缓存策略的
失效场景。

**自测问题**：Cache-Aside 与 Write-Through 取舍？限流放在网关还是应用？
Redis 挂掉时系统行为是什么？

## F6 · 语义质检（AI Provider）

**目标**：接入多模态模型做 Prompt 对齐/质量印象/语义违反检测，结论只进
人工复核，每条带证据束。

**必学技术点**：Provider Adapter 模式（可替换/Mock/故障可观测）；
prompt 快照与版本化；预算/超时/限流边界；批量调用的并发控制；
离线评测集与指标（准确率/误杀率）；证据束（时间码+帧+原始输出引用）；
平台托管模型目录、密钥隔离与不可变 Profile 模型选择。

**任务分解**：
- T1 语义 Provider SPI + Fake Provider（可测）；
- T2 OpenAI 兼容适配器（无 Key 形成语义 ERROR，不静默 Fake）；
- T3 语义 Finding + 证据束落库（UNKNOWN→REVIEW_REQUIRED）；
- T4 离线评测集：标注样本 + 评测脚本 + 指标报告；
- T5 批量调用预算控制与降级。
- T6 平台多模型目录 + 安全目录 API + Profile 版本化选择 + Worker 白名单路由。
- T7 Chat Completions / Responses 双协议多模态适配与 Worker-only Secret 注入。
- T8 单请求真实门禁：合成视觉挑战、无重试预算、脱敏 Evidence 与源码提交绑定。
- T9 完整产品真实门禁：单候选合成 MP4 经 API→MinIO→RabbitMQ→Worker→Provider
  →Java 回写→排名→锁定→导出；进程预算与禁重启共同保证最多一次外部请求。

**完成标准**：Fake Provider 全链路测试；至少两个平台模型的目录/选择/路由
契约自动化通过，浏览器看不到端点与密钥；真实 Provider 有一次真实调用记录；
评测报告能复现；语义结论无一触发自动淘汰。

**当前验证事实（2026-08-24）**：OpenCode Go `gpt-5.6-luna` Responses Adapter
以 3 张程序合成 JPEG 完成 1 次真实请求，HTTP 200；只存在于图片的随机挑战码被
逐字返回，帧顺序与移动图形均判断正确。该记录关闭“至少一次真实调用”门禁，但不
等于完整产品链真实 Provider E2E、真实客户试点或价值证明。

**自测问题**：为什么语义结论不能自动淘汰？Adapter 边界划在哪？
评测集如何防止"调参凑指标"？为什么模型选择必须固化进 Profile 版本？
为什么同一个逻辑模型 ID 不能原地换绑另一个实际模型？

- T4 结论：`PILOT_VALUE_PROVEN` 或 `PILOT_NOT_PROVEN`
  （只依据数据，不依据愿望）。

**完成标准**：至少一个真实批次完整走完；报告数据可复现；
结论措辞与证据一致。
