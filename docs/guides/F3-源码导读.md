## 2. 核心 ★ 索引

| 核心 | 位置 | 解决什么问题 |
|---|---|---|
| Presigned 直传 | StoragePort.presignPut | 字节不过应用服务器：省带宽、省内存、天然并发 |
| 先落库再发凭证 + abort 补偿 | BatchService.registerCandidate | 防孤儿行/孤儿分片会话 |
| 分片号从 1 连续校验 | UploadService.completeMultipartSession | S3 不查"分片齐不齐"，缺片合并=截断视频 |
| 完成时三重校验 | UploadService.verifyAndFinalize | 存在性/大小一致/媒体签名——谎报与截断都现形 |
| INVALID 必带证据 | CandidateMapper.markInvalid | 每条坏文件都能回答"当时为什么" |
| 批次绑定版本行 | V3 迁移 + BatchService.create | F2 版本化的兑现：历史批次永远按创建时标准 |
| UPLOADED 查无对象只报告不降级 | ReconcileService | 掩盖存储故障比数据漂移更危险 |
| Port-Adapter | StoragePort / S3StorageAdapter | 换存储实现业务零改动；测试换容器零改动 |
| DataSize/Duration 配置绑定 | StorageProperties | "32MB"/"PT30M" 可读配置的正确类型 |
| 内外双 endpoint | S3StorageAdapter | 服务端走容器内 MinIO，presigned URL 走浏览器可达域名；签名主机名不能事后替换 |

## 3. 三大设计详解

### 3.1 为什么 Presigned 直传而不是走后端中转

```text
中转：客户端 → 应用服务器 → MinIO      字节流穿应用两跳
直传：客户端 →（presigned URL）→ MinIO   应用只签 URL、收确认
```

直传 wins：应用服务器不碰大文件（内存/带宽/超时全解放）；上传并发
能力由 MinIO 承担（S3 语义水平扩展）；断点续传语义天然属于客户端与
MinIO 之间。代价：完成状态需要客户端回执 + 服务端校验兜底——
所以有 complete 接口和三重校验，**信任边界永远在服务端**。

### 3.2 分片上传的完整生命周期

```text
登记(>阈值) → initiateMultipart(uploadId)
  → 领分片 URL（按需，S3 限制 1..10000）
  → 客户端逐片 PUT，记下每片的 ETag
  → complete：分片号连续性校验 → CompleteMultipartUpload(按序带 ETag)
  → 服务端 head 总大小 + magic bytes → UPLOADED / INVALID
```

开发中真踩的坑（值得记住）：测试登记 9,000,000 字节、实传 5MB+4MB
= 9,437,184 字节——完成时总大小校验直接判 INVALID。**校验逻辑是对的，
错的是测试数据**；这也说明大小校验真的在保护数据一致性。

### 3.3 字节与元数据分离 → 必须对账

PG 说有、MinIO 没了（对象被误删）；MinIO 有、PG 没记（绕过 API 直写）；
客户端拿了凭证没传；传了没确认。四类漂移对应 ReconcileService 的四项报告：
`missingObjects / orphanObjects / awaitingUpload / uploadedNotCompleted`，
外加一个修复动作：超时会话自动判 INVALID（带证据）。
注意 ★：missingObjects 只报告不降级——元数据降级会掩盖存储层故障。
