# F6.1 源码导读 · 平台多模型目录与用户选择

> 目标：平台统一保管模型端点和 API Key，用户只选择平台批准的模型；
> 这个选择随 Quality Profile 版本冻结，并在 Worker 证据中可追溯。

## 1. 先记住三个角色

| 角色 | 能看见什么 | 负责什么 |
| --- | --- | --- |
| 平台运维方 | 完整目录、端点、Key 环境变量和 Key | 接入、启停、轮换与成本治理 |
| FrameFlow 用户 | 模型名称、说明、接入协议、实际模型名、可用状态 | 在 Quality Profile 中选择 |
| Worker | 完整目录和自身进程内的 Key | 按已冻结 `modelId` 路由并留下证据 |

用户不能填写自定义 URL 或 API Key。这不是少做一个表单，而是产品安全边界：
浏览器、业务数据库和 Profile JSON 都不应成为凭据容器。

## 3. 目录为什么只保存 `apiKeyEnv`

```json
{
  "id": "balanced-v1",
  "model": "vendor-vision-model",
  "baseUrl": "https://provider.example/v1",
  "apiKeyEnv": "FRAMEFLOW_MODEL_BALANCED_V1_API_KEY",
  "enabled": true
}
```

`apiKeyEnv` 是环境变量的名字，不是 Key。部署时 Java 和 Worker 得到相同的
`FRAMEFLOW_SEMANTIC_MODEL_CATALOG_JSON`，但真实
`FRAMEFLOW_MODEL_BALANCED_V1_API_KEY` 只注入 Worker。Java API 再把完整目录
映射为不含 `baseUrl/apiKeyEnv` 的安全响应，浏览器因此没有取得秘密的路径。

容器部署不能凭空继承目录里动态命名的 Key。`FRAMEFLOW_WORKER_PROVIDER_ENV_FILE`
指向单独的绝对路径 env-file；Compose 只把它挂给 Worker。部署校验要求文件为
当前操作者所有、`0600`、非 symlink，并拒绝任何不在 enabled 目录中的额外变量。
`infra/scripts/capture-provider-secrets.sh` 从无密钥目录读取变量名，再隐藏读取 Key，
不会把值回显到终端或命令行参数。

目录解析采用白名单字段、唯一 ID、合法 URL、合法环境变量名、受支持 Provider
和 enabled 默认项检查。显式目录一旦损坏，Java 启动失败；Worker 若在运行时
遇到损坏目录则产生语义 `ERROR`。两边都不能悄悄退回 legacy 路由。

## 4. 一次模型选择如何走完全链

```text
GET /api/v1/semantic-models
  → 前端只列 enabled 模型
  → 用户在 Quality Profile 勾选 AI 辅助复核并选择 modelId
  → Java 再次校验白名单
  → Profile vN 的 spec 永久保存 semantic.modelId
  → Batch 引用 Profile vN
  → Worker 从同一目录按 modelId 精确查找
  → 读取该条目的端点、实际模型和专属 Key 环境变量
  → Provider 调用
  → Evidence 保存 modelId + model，不保存端点或 Key
```

前端校验只是及时反馈，Java 入库校验才是安全边界；Worker 再校验一次，是为了
防止存量脏数据或平台目录变化把媒体发往错误模型。

### 4.1 `provider` 代表线协议

| provider | 请求路径 | 图片块 | 文本输出 |
| --- | --- | --- | --- |
| `openai-compat` | `<baseUrl>/chat/completions` | `image_url` | `choices[].message.content` |
| `openai-responses` | `<baseUrl>/responses` | `input_image` | `output[].content[].output_text` |

不能看到 Base URL 以 `/v1` 结尾就默认它是 Chat Completions。协议配错可能直接 4xx，
也可能返回 200 却只处理文字；两种情况都必须作为 Provider ERROR 进入人工复核。

## 5. 为什么省略默认模型也要写回 Profile

Profile 是不可变快照。假设今天默认模型是 `balanced-v1`，下周平台把默认值
改成 `quality-v2`：如果历史 Profile 只保存“使用默认模型”，同一个 Profile
重跑时就会换模型，结果无法复现。

因此，新 Profile 在 `semantic.enabled=true` 且调用方省略 `modelId` 时，Java
会把“当时的默认 ID”写进 JSONB 后再发布。旧数据库中缺少 `modelId` 的版本不
做迁移，Worker 仍按兼容默认项读取，避免改写已发布历史。

同理，`balanced-v1` 一旦发布就不能原地换绑另一个实际模型。升级时应创建
`balanced-v2`；停用 v1 只阻止新 Profile 选择，历史证据仍保留其 ID。

## 6. 失败语义

| 情况 | 行为 |
| --- | --- |
| 用户选择未知或已停用模型 | Java 拒绝发布 Profile |
| 前端目录加载失败或没有 enabled 项 | 禁止提交已启用 AI 的 Profile |
| Worker 遇到未知/停用模型 | 逐语义维度产出 `ERROR`，不换模型 |
| 对应 Key 或端点缺失 | 逐语义维度产出 `ERROR`，不换 Fake |
| Provider 超时、网络失败、响应损坏 | 逐语义维度产出 `ERROR`，进入人工复核 |
| 显式 `FRAMEFLOW_SEMANTIC_PROVIDER=fake` | 仅测试/演示走确定性 Fake |

上述语义错误都不能触发 `AUTO_REJECT`，也不能伪装为视频本身的
`ANALYSIS_ERROR`。它们表示“模型建议不可得”，所以交给人工复核。

## 7. 兼容模式与真实调用边界

未配置 `FRAMEFLOW_SEMANTIC_MODEL_CATALOG_JSON` 时，系统合成唯一逻辑项
`platform-default`，继续读取旧的 `FRAMEFLOW_SEMANTIC_BASE_URL`、
`FRAMEFLOW_SEMANTIC_API_KEY` 和 `FRAMEFLOW_SEMANTIC_MODEL`。这是部署兼容，
不是多模型之间的自动降级。

本功能的目录、选择、路由、脱敏和错误路径可以完全离线自动化；但自动化不能
证明真实供应商端点可达，也不能证明模型确实理解了关键帧。真实 Provider 调用
仍需单独授权和证据记录，在调用前必须再次通知所有者。

OpenCode Go 的 `gpt-5.6-luna` 示例目录位于
`experiments/fixtures/pre-f9-correctness/model-catalog.opencode-go-luna.example.json`。
[OpenCode Go 官方文档](https://opencode.ai/docs/go/#endpoints)把它路由到 Responses API，
并在[隐私表](https://opencode.ai/docs/go/#privacy)标注最长 30 天数据保留；第一次只能
发送合成媒体。真实客户媒体还需单独完成供应商隐私、地域、合同与留存决策。

未来执行步骤见 `docs/guides/F6-真实Provider门禁.md`；本轮离线证据见
`docs/evidence/F6.1-Responses-Provider离线门禁.md`。
