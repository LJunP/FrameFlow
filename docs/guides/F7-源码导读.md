## 2. 核心 ★ 索引

| 核心 | 位置 | 解决什么问题 |
|---|---|---|
| 双指纹 | phash.py + candidates 两列 | 精确重复（SHA-256 永不误判）与近重复（dHash 容忍再压缩）各司其职 |
| 资格门留痕 | RankingService 排除项写 excluded_reason | 排名不是无声淘汰——每个出局者都有原因可查 |
| UNKNOWN 不扣分 | score() 的跳过分支 | 模型"不确定"不是候选的错；扣分会把好视频挤下去 |
| 并查集聚类 | UnionFind | 近重复是等价关系（传递性），union-find 天然契合 |
| 确定性并列决胜 | 排序 (score desc, candidateId asc) | 没有随机性 → 同输入同输出 → 快照可复现 |
| 快照固化 | ranking_snapshots/entries 只增 | 事后争议时"当时的排名"永远可查 |
| 人工不改机器 | selection_items 两列并存 | 导出各表各的，审计能还原"谁改了什么" |
| 条件更新锁 | lockIfDraft / adjust 的 EXISTS | 并发双击只有一个生效，不需要应用层锁 |
| CSV 最小引号 | SelectionController.csv | 只有含分隔符才包裹——任何解析器都吃 |

## 3. 三个关键问题（自测题剧透）

### 聚类阈值如何版本化？
阈值配置在 **profile spec**（`duplicates.hammingThreshold`）里 → 随 profile
版本行冻结（F2 机制）→ 批次绑定具体版本行（F3 机制）→ 快照再冗余记录
当时阈值 + 独立的 algorithm_version。四层下来：任何历史快照都能回答
"当时用的什么阈值、什么算法"。

### 为什么人工调整不改机器结果？
如果人改了就把 machine_pick 覆盖掉，"机器到底选了什么"就永久丢失——
模型评测（F6 的准确率/误杀率）恰恰需要机器原始输出做对照。
两列并存 = 机器结果是被保护的训练/评测资产，人工意见是叠加层。

### Snapshot 固化解决什么问题？
排名是"当时的真相"：之后重跑质检、改权重、发新版本标准，都不该篡改
历史结论。导出的交付物引用快照 id → 交付永远可复现、可解释、可追责。
