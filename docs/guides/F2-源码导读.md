## 3. 每个索引/约束的理由（面试常问）

| 约束/索引 | 为什么 |
|---|---|
| `uq_projects_team_name (team_id, name)` | 项目名冲突的数据库最后防线；应用查重挡 99%，UNIQUE 挡并发 1% |
| `idx_projects_team (team_id)` | 列表页按团队查项目是最热查询，主键索引帮不上外键列 |
| `idx_briefs_project (project_id, id)` | 快照列表按 (项目, 时间序) 取；复合索引正好覆盖排序 |
| `uq_profile_version (profile_id, version_no)` | **引用隔离的物理保证**：版本号唯一且只增，发布新版本永不改旧行 |
| `lock_version` 列 | 乐观锁载体；无 UPDATE ... WHERE lock_version=? 就无法检测丢失更新 |
| briefs 无 `updated_at` | 不可变数据没有"最后修改"语义——列的缺失本身就是设计声明 |

## 4. 三大设计详解

### 4.1 不可变快照（Brief）

问题：批次（F3）要引用"创建当时的创作要求"。若 Brief 可改，历史批次的
质检依据就漂移了，出了问题无法复现。

解法：**快照行永不 UPDATE**（Mapper 里物理上没有 Update 方法），
"修正 = 追加新行 + `current_brief_id` 指针前移"，两步同一事务。
历史行原地不动，任何时间点的配置都可精确还原。

### 4.2 版本化配置（Quality Profile）

问题：质检标准会迭代，但进行中的批次必须按"它创建时"的标准判。

解法：profile 是壳，标准全部在 version 行里（JSONB）。批次引用
**版本行**而非 profile 本身 → 发新版不影响任何历史批次。
版本号生成用"查 max + 1 插入 + UNIQUE 兜底 + 冲突重试一次"，
并发发布也绝不复用版本号（有专门的测试：外部占用 v2 后服务端发的是 v3）。

### 4.3 乐观锁（丢失更新问题）

两个运营同时编辑同一项目：A 先提交，B 后提交——B 手里的旧数据会把 A 的
修改**无声覆盖**。解法：每次更新带 `lockVersion`，UPDATE 的 WHERE 匹配
不上就 0 行 → 409 VERSION_CONFLICT，逼客户端重新读取再改。
选乐观而非悲观锁：配置类数据冲突概率低，不值得为它占数据库行锁。

## 5. 契约先行与架构守护（T4）

- `docs/api/frameflow-v1.yaml` 是**手写的唯一权威**；springdoc 运行时生成
  `/v3/api-docs`。一致性测试**双向**对比：契约里的接口运行时必须存在，
  运行时的接口契约里必须写了——"先改契约再写代码"由测试强制。
- ArchUnit 三条规则把 docs/02 §3 的模块边界变成测试：product 碰 identity
  数据层、web 直连 repo、shared 反向依赖业务模块，任何一条都会红。
  （本功能开发中真踩了 ArchUnit 的坑：用它的专用 JUnit 引擎时 surefire
  报 "Tests run: 0"——规则假绿。改用普通 @Test + ClassFileImporter 才
  真正生效。教训：**守门的东西本身也要验证它真的在守门**。）
