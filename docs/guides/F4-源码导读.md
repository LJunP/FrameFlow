## 2. 核心 ★ 索引

| 核心 | 位置 | 解决什么问题 |
|---|---|---|
| 幂等 = 条件状态迁移 | IngestionService + runMapper.finalizeIfRunning | 重复回放零副作用，不需要去重表 |
| ANALYSIS_ERROR ≠ AUTO_REJECT | IngestionService + pipeline.py | 系统故障与视频不合格是两个世界（红线） |
| Publisher Confirm | DispatchService.publishConfirmed | broker 不确认就当失败，事务回滚可重试 |
| 条件迁移当锁 | candidateMapper.markAnalyzing | 连点两次"分析"只派发一轮 |
| prefetch = 背压阀门 | worker config + consume.py | broker 堆着没关系，worker 按能力取 |
| 毒消息三级处理 | consume.on_message | 重试超限 → 回写失败 + ack，不无限循环 |
| DLQ + 重放 | RabbitConfig + MqAdminController | 毒消息有停尸房、有复活通道 |
| 检测器故障语义 | pipeline.analyze 的 DetectorError 分支 | 缺 ffprobe/解不开 = ANALYSIS_ERROR |
| 缺测量不冒充 PASS | rules.py + frames.py | Profile 启用的测量缺失、视频零可解码帧都抛 DetectorError |
| 证据必留 | findings 表（含 passed=true 行） | 每条判定都能回答"当时看到什么" |

## 3. 三个关键问题的答案（自测题的剧透式讲解）

### 3.1 消息丢失/重复/乱序怎么防？

```text
丢失：Publisher Confirm（Java→MQ）+ 消费者手动 ack（处理完才确认）+ 
      崩溃时未确认消息自动重投（broker 行为，有专门测试）
重复：投递语义是"至少一次"，防重复不靠 MQ 靠接收方——
      IngestionService 的条件状态迁移让第二次回写变成 no-op
乱序：无所谓——每个任务自包含（runId+spec 都在消息里），任务之间
      没有顺序依赖；结论回写按 runId 幂等合并
```

### 3.2 幂等键怎么设计？

不是"键"，是"状态机"：`UPDATE ... WHERE id=? AND status='RUNNING'` 的
影响行数就是互斥裁决。第一个到达者把 run 从 RUNNING 推走，后来者一律
返回既有状态。**数据库的行级锁替你做了分布式锁**。

### 3.3 背压为什么必要？

一个批次最多 300 条视频，每条要下载+解码（秒级 CPU）。如果没有背压，
worker 一次抓 300 条全部开始处理 → 内存爆、下游 MinIO 连接爆。
prefetch=2 意味着"最多 2 条在途"，处理完一条才拿下一条——
**broker 本身就是缓冲区，消费者自己控制流速**。

## 4. 本地跑真实流水线（三件套齐活）

```bash
docker compose -f infra/local/docker-compose.yml up -d   # PG + MinIO + RabbitMQ

# 终端 1：Java 后端
./mvnw spring-boot:run -pl frameflow-app
# 终端 2：Python 3.11 worker
cd frameflow-ai-worker && ./.venv/bin/python -m frameflow_ai

# 然后按 F3 导读建项目/批次/上传/关闭，再：
curl -X POST http://127.0.0.1:18080/api/v1/batches/<id>/analyze \
  -H "Authorization: Bearer $TOKEN"
# 观察两个终端的日志：任务出队 → 检测 → 回写 → 候选状态变化

./mvnw test && cd frameflow-ai-worker && ./.venv/bin/python -m pytest tests -q
```

如果宿主机没有 `ffprobe`，可先用仓库的只读 Docker 适配器放到 PATH：

```bash
# 在仓库根目录执行
mkdir -p .tmp/pre-f9-bin
ln -sf "$PWD/scripts/ffprobe-via-docker.sh" .tmp/pre-f9-bin/ffprobe
cd frameflow-ai-worker
PATH="$PWD/../.tmp/pre-f9-bin:$PATH" ./.venv/bin/python -m frameflow_ai
```

## 5. 开发中真踩的坑

1. **缓存连接的 close() 是假的**：模拟"worker 崩溃后消息重投"时，
   `createConnection().close()` 只是把连接归还 Spring 的缓存池，物理
   通道还挂着未确认消息，永远不会重投。必须用
   `getRabbitConnectionFactory().newConnection()` 建物理连接。
2. **架构规则把作者自己抓了**：AnalysisController 直接注入 FindingMapper
   违反 web→repo 规则（连返回类型引用 repo 行对象都算）。被抓后抽出
   AnalysisQueryService——守门规则真的在守门，这就是它存在的意义。
3. **测试容器的 RabbitMQ 凭据**：容器默认 guest/guest，yml 里是开发值，
   不覆盖就 ACCESS_REFUSED——测试环境的"显而易见"往往不显而易见。
