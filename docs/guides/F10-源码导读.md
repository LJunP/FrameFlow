## 3. 两条信号调用链

### Java

```text
HTTP request
  → CorrelationIdFilter 校验/生成 X-Request-Id
  → MDC(request_id, http_method)
  → Controller / Service
  → FrameFlowMetrics 有限枚举 Counter
  → Micrometer PrometheusMeterRegistry
  → GET /actuator/prometheus
  → Prometheus → Alertmanager / Grafana

stdout Logstash JSON → Docker RFC5424 syslog driver → host loopback UDP
  → Alloy syslog receiver → Loki → Grafana logs panel
```

### Worker

```text
main
  → configure_json_logging
  → WorkerMetrics.serve(:9108, 独立线程)
  → start_worker
  → _handle_message(JSON 校验)
  → on_message(analyze + report)
  → succeeded / analysis_error / report_rejected / requeue / invalid_message
  → ACK / republish+ACK / NACK-to-DLQ
```

畸形消息直接进 DLQ 并记 `invalid_message`，不会让消费循环崩溃，也不会回写成
视频不合格。`run_id` 只进日志，不进 Prometheus label。

## 4. 指标口径

| 指标 | 标签 | 含义 |
| --- | --- | --- |
| `frameflow_analysis_dispatch_total` | `outcome=confirmed|failed` | Rabbit Publisher Confirm 结果 |
| `frameflow_analysis_ingestion_total` | `outcome=succeeded|analysis_error|duplicate` | 幂等回写分支 |
| `frameflow_dependency_degradation_total` | `dependency=redis`, `operation` | 缓存/限流降级 |
| `http_server_requests_seconds_bucket` | route/status 等有限框架标签 | 可跨实例聚合的 HTTP histogram |
| `frameflow_worker_messages_total` | `environment,outcome` | Worker 消息终态 |
| `frameflow_worker_processing_seconds_bucket` | `environment` | Worker 处理耗时 |
| `frameflow_worker_republished_messages_total` | `environment` | attempt+1 重投 |
| `frameflow_worker_ready` / `inflight` | `environment` | 消费循环与在途量 |
| `rabbitmq_detailed_queue_messages_ready` | `vhost,queue` | RabbitMQ 官方 detailed endpoint 的待消费消息数 |

为什么不用 `batchId/runId/userId` 作 label：Prometheus 每组 label 值生成一条时间序列，
业务 ID 无限增长会造成内存与磁盘爆炸。排障用 Loki JSON 字段做按需检索。

`application.yml` 必须开启 `percentiles-histogram.http.server.requests=true`；只配置
客户端 P95 会让多实例无法正确聚合。集成测试直接检查 `_bucket` 确实出现在
`/actuator/prometheus`，避免 Dashboard 有查询、运行时却没有数据。

## 5. 告警与日志

告警分三组思路：

- 可用性：App、Worker、PostgreSQL、Redis、RabbitMQ down；
- SLI：5xx 比例 >5%、HTTP P95 >1s；
- 异步链：`rabbitmq_detailed_queue_messages_ready` >100、Worker 失败突发、Redis
  降级突发。

阈值都有 `for` 窗口，避免一次抖动立刻呼叫。它们是初始工程阈值，真实运行后应按
基线和错误预算校准，禁止为了让演练 PASS 而抬高阈值。

Alloy 没有 Docker socket、API proxy、container discovery 或 inspect 权限。App/Worker
用 Docker syslog driver 将 RFC5424 日志推到每环境独占的宿主 loopback UDP；固定
tag 只允许两类应用日志进入。Docker dual logging cache 仍开启且有界，便于 Loki
中断时查看近期日志；UDP 和 non-blocking buffer 在极端拥塞时可能丢日志，不能把它
写成零丢失审计总线。宿主 Nginx 日志用 `docker-compose.nginx-logs.yml` 显式挂每环境
独立目录，禁止挂整个 `/var/log` 或把 dev/staging 混进同一 Loki project。

RabbitMQ 不再使用归档的第三方 exporter 或额外 monitor 用户。官方
`rabbitmq_prometheus` 插件在 Compose 内网 expose `15692`：基础 `/metrics` 用于
存活与聚合指标，`/metrics/detailed` 只请求 `queue_coarse_metrics` 和
`queue_consumer_count`，避免无边界引入高基数 detailed families。

本地 `alert-sink` 只在 `synthetic-alert-drill` profile。production 启动脚本拒绝
synthetic 模式。真实 receiver 的原始 webhook Secret 保持宿主 root 所有、`0600`；
`render-alertmanager-config.sh` 必须由 root 执行，并把不入库的运行配置设为容器
固定身份 `65534:65534` 所有、`0400`。`observability-stack.sh` 在 Compose 运行前
同时校验 numeric owner 和 mode；不能用宿主用户 `0600`（容器不可读）或 `0444`
（泄露面扩大）冒充正确权限。

本地动态验证中，App/Worker 的 logging driver 均实际解析为 syslog；Loki 查询得到
3 个 stream、39 条样本，且两个应用 service 标签与 payload service 字段均覆盖。
Alloy 固定以 `473:473` 运行、`cap_drop: [ALL]`，没有任何 socket mount。外部
Alertmanager 配置还用官方镜像真实用户完成了读取和 `amtool` 正向检查。

## 6. 备份、恢复与安全不变量

### PostgreSQL

- `pg_dump --format=custom --no-owner --no-privileges`：便于恢复到隔离用户。
- 先写同文件系统随机 staging，生成 restore list、SHA-256、manifest 后原子改名。
- 隔离恢复启动随机 network/volume/container，不发布宿主端口；恢复后验证 public
  table 数与 Flyway 历史，trap 强制删除本次精确命名资源。
- 覆盖目标恢复默认 dry-run；要求 environment/project/service/database 全部显式、
  typed confirmation 完全匹配，并先验证同一 project 的 App/Worker/Web 已停止，
  再生成目标现场备份。任一写入服务仍运行时，在 mutation 前立即拒绝。
- 已验证的本地事实：dump restore list 为 169 个对象；随机隔离恢复后有 18 张
  public 业务表和 6 条 Flyway 历史。它不等于 production RTO/RPO 已测得。

### MinIO

- 复用 `minio-init` 已注入的凭据，Secret 不读回宿主 shell。
- 当前对象镜像生成逐文件 SHA-256 和 inventory；隔离恢复再下载一遍逐字节比对。
- `versionHistoryIncluded=false` 是硬事实：逻辑镜像不是历史版本灾备。production
  仍需独立站点复制/对象锁，这个外部门禁不能用本地 current-object PASS 替代。
- 已验证的本地事实：6 个 current objects 在隔离 MinIO 中逐对象下载并通过
  SHA-256/逐字节比对；未覆盖历史版本。

### Redis 监控 ACL

- exporter 用户没有 key pattern，也没有 `GET`、`SCAN` 或 `CONFIG` 权限；启动前
  用 `ACL DRYRUN` 验证 `INFO` 允许、业务 key `GET` 拒绝。
- 已验证 Redis 重启后的 runtime ACL reprovision：专用凭据恢复成功，Prometheus
  再次记录 `redis_up=1`。这不证明 production 值班人流程已经演练。

### 路径与环境守卫

`lib/common.sh` 由入口先传入已解析的 root 并检查 sentinel，不从 `$0` 猜自己的
路径。每个 Compose 操作都显式接收 `--env-file`、environment、project 和 service，
再核验 `FRAMEFLOW_ENV` 与容器 Compose label；不会因从不同 cwd 运行而串环境。

F9 `install-ops-bundle.sh` 把 manifest 对应 Git commit 的 tracked `infra/` 安装到
`/opt/frameflow/ops/current`。systemd 的非 root `frameflow` 身份通过
`root:frameflow 0640` 配置/env、`0750` 父目录和 `0770` 备份目录读取所需文件；
隔离 Linux 身份探针已执行 `run-scheduled-backups.sh --validate-only` 并通过。

## 7. 故障演练边界

- Redis/DB/Worker：只 `stop` 精确 service，trap 恢复，不删卷。
- MQ 积压：只创建随机 `frameflow.drill.*` durable 队列，设置 10 分钟 `x-expires`，
  正常路径严格删除；不向业务 exchange 发消息。
- production 永久拒绝；staging 需要额外 gate；默认 dry-run。
- 结果使用 `HARNESS_PASS`，只表示注入/观察/恢复/清理机制成功，不表示业务 RTO、
  production 韧性或真实告警触达已证明。
- 已验证的本地事实：MQ 专用队列注入 120 条消息，连同 Worker、PostgreSQL、Redis
  三类注入，共四类均得到 `HARNESS_PASS` 并完成精确恢复/清理。
