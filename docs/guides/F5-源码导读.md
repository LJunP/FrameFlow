## 2. 核心 ★ 索引

| 核心 | 位置 | 解决什么问题 |
|---|---|---|
| Lua 原子令牌桶 | RedisRateLimiter | "读-算-扣"竞态：并发请求不会双双通过 |
| 令牌桶 vs 固定窗口 | 同上注释 | 固定窗口的"边界突刺"问题 |
| fail-open | tryAcquire 的 catch | 限流器挂了放行而不是瘫痪业务（取舍见 §3） |
| Cache-Aside 写侧 | 三处 evict 调用 | 改数据删缓存，读时重建——最不容易出错的缓存模式 |
| 空值哨兵 | ProgressCacheService.store(null) | 防穿透：不存在的 key 也缓存 60s |
| 互斥重建 | getOrLoad 的 SETNX 锁 | 防击穿：热 key 过期瞬间只有一个请求查库 |
| 缓存优先 vs 校验优先 | get() vs progressOf() | 授权校验与穿透防护的诚实取舍（见 §4） |

## 3. 三个经典取舍题（自测题的答案预演）

### Cache-Aside vs Write-Through

```text
Cache-Aside（本项目）：读时回填，写后只删缓存。
  优点：实现简单；缓存故障不影响写路径；失效语义明确。
  代价：删缓存到下次读之间有一次 miss（可接受）。
Write-Through：写时同步更新缓存。
  优点：缓存永远新鲜。
  代价：写路径耦合缓存可用性——Redis 挂了写入也失败，违背
        "Redis 永远可丢失"的原则（docs/02 §4.3）。
```

### 限流放在网关还是应用？

网关（Nginx/未来 API Gateway）适合**全局**粗粒度（IP 级防扫描）；
应用层适合**业务语义**细粒度（每邮箱、每团队、每 API key）。
登录限流放应用层是因为"按邮箱"这个维度网关看不见（请求体）。
F9 上线后两层都会有，各管各的维度。

### Redis 挂掉时系统行为是什么？（已在演练中实测）

```text
登录   → 正常处理（fail-open，WARN 日志）
进度   → 直查数据库（短暂变慢，功能不变）
写失效 → 跳过，靠 30s TTL 自然过期（最坏 30s 旧数据）
```

一个演练中撞见的真实细节：Redis 重启后，**旧进程的 Lettuce 连接池**
需要重建，短窗口内继续降级——生产重连时长值得观测（见演练记录 §3）。

## 4. get() 与 progressOf() 为什么长不一样

`get()`（批次详情）：先做归属校验（必然查库），缓存只省**聚合查询**——
授权优先，穿透防护意义不大（反正已查库）。
`progressOf()`（轮询专用）：缓存优先，不存在的批次写**哨兵**——
高频轮询场景下，恶意扫 ID 连主键查询都省掉，但授权仍只对存在的批次执行。
**没有银弹，只有按读路径的职责选型**——这就是两个方法并存的理由。

## 5. 本地复现

```bash
docker compose -f infra/local/docker-compose.yml up -d   # 含 redis
./mvnw spring-boot:run -pl frameflow-app

# 限流实验：连打 7 次错误密码 → 第 6 次 429
for i in 1..7; curl -X POST :18080/api/v1/auth/login -d '{"email":"a@x.com","password":"x"}'

# 缓存实验：GET /batches/1/progress 后看 key 与 TTL
docker exec frameflow-local-redis redis-cli keys 'batch:*'
docker exec frameflow-local-redis redis-cli ttl batch:progress:1

```
