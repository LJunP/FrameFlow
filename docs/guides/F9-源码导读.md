13. `promote-release.sh` → `smoke-test.sh` → `rollback.sh`：发布、证据、回滚闭环。

## 3. 为什么这样设计

### 3.1 Build once，而不是每个环境重建

经所有者以后明确触发的 CI publish job 在主线 SHA 上各构建一次 app/worker/web，
Registry 返回 Digest 后生成
`image-manifest.json`。dev、staging、production 消费同一 `immutableRef`。如果晋级时
重新 build，即使 Git SHA 相同，基础镜像或 Python 依赖变化也可能生成不同字节，
staging 的结论就不能证明 production 的镜像。Worker 额外用精确 lock 限制重建漂移；
正式晋级仍只认 Digest。

### 3.2 dev 与 staging 如何在同一 VPS 隔离

两套 Compose 分别叫 `frameflow-dev`、`frameflow-staging`，不写 `container_name`，
各自产生独立 network/volume。数据库名、用户、密码、Redis 实例、RabbitMQ 用户与
VHost、MinIO 凭据与 Bucket、JWT key、loopback 端口、域名全部不同。

宿主机只有一个 Nginx 占用 80/443：按域名转发到两个不同 loopback 端口。
数据库/MQ/Redis 没有宿主端口，也没有把两个 Docker network 接起来。
production 使用独立 VPS；“同一个 Compose project 换变量”不算生产隔离。

### 3.3 为什么 MinIO 要两个 endpoint

容器内 Java/Worker 用 `http://minio:9000`；浏览器拿到的 presigned URL 必须是
`https://media.<domain>`。Nginx 对媒体请求不能重写 Host、路径或查询参数，因为这些
都参与 SigV4。MinIO CORS 只允许当前 Web origin。Smoke 会实际发 PUT preflight；
只测 `/minio/health/live` 不能证明浏览器能上传。

### 3.4 Secret 与 JWT key

模板不含可用 Secret。远程 app 固定
`FRAMEFLOW_ALLOW_EPHEMERAL_RSA_KEY=false`，通过 Compose secret 挂载公私钥文件；
缺一项就启动失败。这样重启/回滚不会让全部 refresh token 突然失效。真实 Provider
Key 不在 Compose 模板、manifest、浏览器或日志中；未来仍须所有者再次确认后单独注入。
真实模型启用时，`FRAMEFLOW_WORKER_PROVIDER_ENV_FILE` 指向一个当前部署操作者所有、
`0600` 的绝对路径文件。Compose 只给 Worker 加载它；校验器要求文件中的变量名与
enabled 目录项精确一致，拒绝额外变量、缺 Key、symlink 和宽松权限。可用
`capture-provider-secrets.sh` 隐藏采集，Key 不出现在 shell history 或命令行参数中。

App 运行身份固定为 `10001:10001`。Compose 的 file secret 不会替宿主文件重映射
UID，因此 `generate-jwt-keypair.sh --apply` 必须以 root 执行，并把 key 安装为数字
owner `10001:10001`：私钥 `0400`、公钥 `0444`。保留 root-owned `0400` 会让非 root
App 启动即失败；改成 world-readable 私钥又会泄密，两者都不接受。

### 3.5 为什么 CD 不直接 SSH

当前授权明确把 VPS、SSH、DNS 与真实生产操作留给所有者。CD workflow 因而只接受
手工 dispatch、GitHub protected Environment 审批和精确确认短语，下载已发布的
Digest manifest，并向 GitHub API 核验 source run 的成功状态、workflow、主线分支、
run ID 与 head SHA。随后 checkout 该 SHA，打包完整 tracked `infra/`、
`OPS_GIT_SHA`、精确文件集 checksum、manifest 和 `release.env`。它没有 SSH key、
host 或自动部署步骤。这是有意保留的物理门禁，不是伪称“已自动上线”。

下载并解压 handoff 后，先在 bundle 根执行：

```bash
sha256sum --quiet -c HANDOFF_SHA256SUMS
infra/scripts/install-ops-bundle.sh \
  --bundle-root "$(pwd -P)" \
  --manifest "$(pwd -P)/image-manifest.json"
```

安装器会再次要求 `OPS_GIT_SHA` 等于 manifest SHA，
并拒绝缺失、额外、越界、symlink 或摘要不一致的 `infra/` byte。checksum 负责发现
传输/存储损坏，不是独立签名；下载来源和 GitHub protected Environment 仍是信任边界。

## 4. 本地验证（不需要 Provider）

最小离线门禁：

```bash
infra/scripts/test-f9-scripts.sh
bash -n infra/scripts/*.sh
git diff --check
```

它覆盖：四套 Compose 解析、`latest`/`container_name` 扫描、模板隔离矩阵、恶意 env
不执行、JWT 公私钥同路径负例、Provider Secret `0600`/精确键集/Worker-only 注入、
无确认禁止覆盖、manifest 正反例、Nginx 渲染和所有破坏性脚本 dry-run。

Web 依赖还有一条必须保留的安全门禁：本轮已将被已知 RCE/DoS 公告
覆盖的 `next@15.3.3` 升到同一主版本的 `15.5.23`，并将内置 `postcss`/`sharp`
锁到当时已修复版本。CI 使用 npm 官方审计端点拒绝 high/critical；2026-08-24
本地结果为 0 vulnerability。这只是时点性依赖事实，每次真实发布前都必须重跑，
不能把一次绿灯当成永久安全证明。

完整本地栈（会构建镜像并启动容器，不发真实 Provider 请求）：

```bash
cp infra/local/env.example infra/local/.env

infra/scripts/smoke-test.sh --environment local \
  --compose-file infra/local/docker-compose.yml \
  --env-file infra/local/.env --base-url http://127.0.0.1:3000
```

## 5. 以后由所有者执行的部署顺序

以下是 Runbook，不是本轮已执行记录。

1. 在目标 Ubuntu VPS 先 dry-run `bootstrap-vps.sh`，审核后再带 `--apply` 和确认短语；
2. 复制 `env.example` 到 `/etc/frameflow/<env>/frameflow.env`，安装为
   `root:frameflow 0640`，再替换全部 Secret、域名、Digest；这个路径也由 F10
   systemd 备份任务复用；
3. 跑单环境校验；同宿主 dev/staging 再跑 `--matrix`，必须 PASS；
4. 用 `generate-jwt-keypair.sh` 生成环境独占 key，核对 owner `10001:10001`，绝不
   拷贝到仓库；
5. 若启用真实模型，把无密钥目录写入主 env；用 `capture-provider-secrets.sh` 在
   `/etc/frameflow/<env>/worker-provider.env` 隐藏采集已轮换 Key，核对 owner 与 `0600`，
   再运行环境校验；该文件只注入 Worker；
6. 配置两个 DNS 记录；先渲染 `http-bootstrap` 到
   `/etc/nginx/sites-enabled/frameflow-<env>.conf`；
7. 所有者执行证书请求，再渲染 HTTPS；安装续期 timer；
8. 从 CI 下载 handoff，先校验 `HANDOFF_SHA256SUMS`，再用 bundle 内
   `install-ops-bundle.sh --bundle-root ...` 原子安装 manifest 同一 Git commit 的
   运维包，最后执行 `promote-release.sh`；
9. Smoke 必须验证首页、HSTS、内部依赖、Worker、MinIO health 和 CORS；
10. staging 用 `rollback.sh --ack-forward-only-db` 做一次回滚，再晋回同一候选版本；
11. production 还必须满足 F10 监控/备份/恢复门禁和 GitHub Environment 人工审批。

一旦 Smoke 失败，先保留日志与 manifest；不要改阈值、换 tag 或把失败手工登记为成功。

## 6. FACT / INFERENCE / UNKNOWN

### FACT

- 本仓已具备三种非 root 多阶段 Dockerfile、local 全栈和三套远程 Compose 模板；
- 远程镜像变量必须包含 tag + sha256 Digest，模板实际部署会 fail-closed；
- 普通 PR/push 的 CI 不写 Registry；手工 image publish 还受确认短语和 protected
  Environment 保护；CD handoff 没有 SSH/部署步骤；
- 发布/回滚/证书/VPS 脚本默认 dry-run，`--apply` 还需环境匹配确认短语。
- §4.1 记录的 `app` / `worker` / `web` 本地镜像构建、non-root 身份、RabbitMQ `4.3.5` 基线与 `frameflow-local` 全栈 Smoke 已完成动态验证。

### INFERENCE

- 在满足 Ubuntu、Docker Compose、DNS、证书、Registry 权限和真实 Secret 前提下，
  模板应可作为人工部署起点；该判断仍需目标 VPS 上的实际 Smoke 才能升级为 FACT。

### UNKNOWN（外部门禁）

- registry 中可用于 `repo@sha256:...` 的 App/Worker/Web 完整 Digest、GitHub Actions
  在远程 runner 的真实执行结果与 GHCR 产物；本地 image ID 和上游 RabbitMQ
  Digest 不能关闭该门禁；
- 目标 VPS 发布前仍须按当时官方安全公告重新审计 Web 依赖，并重跑全部 Web/镜像
  门禁；当前本地 `npm audit` PASS 不是未来发布时点的安全保证；
- VPS 规格、公网、防火墙、DNS 传播、ACME 签发、真实域名访问；
- production 发布、production 回滚、production 数据恢复；
- production Provider 网络/成本/稳定性与真实试点价值。

因此不能据此宣布线上已可访问、恢复演练成功、试点价值成立或项目完成。
