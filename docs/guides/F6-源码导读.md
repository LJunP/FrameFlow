# F6 源码导读 · 语义质检（AI Provider）

> 质检的另一半：确定性维度说"格式对不对"，语义维度说"内容对不对"。
> 本功能的灵魂是一句话：**模型只有建议权，没有生杀大权。**

## 2. 核心 ★ 索引

| 核心 | 位置 | 解决什么问题 |
|---|---|---|
| 一次 run 两阶段 | pipeline `_run_detectors` | 抽帧一次共用；语义是确定性阶段的"附加题"不是独立流水线 |
| verdict 四值列 | V5 + FindingMapper | PASS/VIOLATE/UNKNOWN/ERROR——确定性用 passed，语义用 verdict，一列两种语义不打架 |
| 语义禁 BLOCKER（双侧） | semantic.py + IngestionService | Python 侧不产生；Java 接收端强制降级——恶意客户端也钻不进 |
| UNKNOWN ≠ 不合格 | IngestionService | VIOLATE/UNKNOWN/ERROR 全进 REVIEW_REQUIRED，人定生死 |
| 不静默伪造模型结论 | semantic.build_provider | 默认走真实适配器；只有显式 `FRAMEFLOW_SEMANTIC_PROVIDER=fake` 才用 Fake |
| 真正发送关键帧 | 两个真实适配器的 `analyze` | JPEG 按协议成为 `image_url` 或 `input_image` data URL，而非只写“帧数量” |
| 协议不靠猜 | semantic.build_provider | `provider` 显式选择 Chat Completions/Responses；URL 或模型名相似也不自动改路由 |
| 无 Key 自动禁用 | 两个真实适配器的 `available` | 缺凭据 → ProviderDisabled → 逐维度语义 ERROR（可观测），不静默切 Fake |
| Provider 失败向人兜底 | semantic.run_semantic | 网络/超时/限流 → ERROR 判定进人工复核，任务本身永不失败 |
| 关键帧预算 | MAX_KEYFRAMES=3 + prompt 截断 | 多帧≠更准只=更贵；钱包的边界写在代码里 |
| 帧证据可核对 | semantic.run_semantic | evidence 保存实际发送 JPEG 的时间码和 SHA-256，而非源文件的替代哈希 |
| 真实调用不失控 | run_real_provider_gate.OneShotPost | transport 最多执行一次；失败不重试，第二次必须重新授权 |
| 可复现评测 | fake 稳定哈希 + 固定数据集 | 同输入永远同报告——评测驱动调参的闭环前提 |
| 多模型选择随版本固化 | QualityProfileService + model_catalog.py | 用户选逻辑 ID，平台托管端点/Key；默认值也在发布时写进不可变 Profile |

## 3. 语义 Finding 的一生

```text
spec.semantic.enabled = true 才会运行（Profile 里显式开关）
  → worker 抽 ≤3 个关键帧（JPEG）+ brief 原文
  → 按 Profile 的 semantic.modelId 在平台 enabled 白名单中精确路由
  → Provider.analyze() 按目录项协议走 Chat Completions 或 Responses 适配器
     （只有显式配置 fake 才走稳定哈希 Fake；缺真实配置则产出 ERROR）
  → 多模态请求 = prompt 文字 + ≤3 个 JPEG data URL
     Chat Completions: messages/content/text + image_url
     Responses: input/content/input_text + input_image
  → 每维度产出 verdict + reason + timecode；证据束保留 prompt、原始输出、
     Provider 版本、关键帧时间码和实际 JPEG SHA-256（evidence JSONB）
  → Java 接收端：语义 BLOCKER? 强制 WARNING
  → 有 VIOLATE/UNKNOWN/ERROR → 候选 REVIEW_REQUIRED
  → 全 PASS → ANALYZED
```

## 4. 评测方法论（T4 的正确打开方式）

`eval/dataset.json` 是**固定考卷**（改它=改考题，指标失去跨版本可比性）；
`evaluation.py` 输出 accuracy / 误杀率 / 待复核率。

**关键认知**：当前存档的基线
（`eval/reports/baseline-fake-2026-08-22.json`：accuracy 0.4）是
Fake Provider 的"随机基线"——它证明的是**评测管道本身可复现**，
不是模型准确率。真实基线的产生路径：
1. 平台按 `F6.1-源码导读.md` 配置无密钥模型目录，并把各目录项的 Key 仅
   注入 Worker；既有单模型部署仍可使用
   `FRAMEFLOW_SEMANTIC_BASE_URL/API_KEY/MODEL` 兼容模式；
2. 重跑 `python -m frameflow_ai.evaluation > eval/reports/baseline-<provider>.json`；
3. 之后每次改 prompt/换模型，重跑对比——这就是"评测驱动调参"。
