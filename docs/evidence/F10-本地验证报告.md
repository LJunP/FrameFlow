- 就绪端点：Prometheus `:19090`、Alertmanager `:19093`、Loki `:13100`、Grafana

  `postgres`、`redis`、`rabbitmq`、`rabbitmq-detailed`、`prometheus`；`pg_up`、

  `FrameFlow Select / Operations` Dashboard 已 provision。
- App/Worker 的 Docker logging driver 实际解析为 `syslog`，目标为当前环境独占的
  `udp://127.0.0.1:15140`，格式为 `rfc5424micro`；Alloy 以 `473:473`、全部
  capabilities 丢弃的身份监听该 UDP 入口，且没有 Docker socket、API proxy、
  container discovery 或 inspect 权限。
- Loki 最终查询到 3 个 stream、39 条样本；Compose service 标签同时覆盖 `app`、
  `worker`，日志 payload 的 service 字段覆盖 `frameflow-app`、`frameflow-worker`。
  Docker dual logging cache 也实际保持开启并通过有界配置校验。
- 05:20:50Z 停 App，Prometheus 由 pending 进入 firing；synthetic sink 在
  05:23:09Z 收到 `FrameFlowAppDown`。05:23:23Z 恢复 App，05:24:09Z 收到
  `resolved`。轮询观察约 142 秒触发、51 秒恢复；健康流量后 active alerts 为 0。
- 改成无 Docker API 的 syslog 架构后，首次动态启动暴露 Alloy volume 虽归属
  `473:473`、但进程仍以 root 且丢弃全部 capability 导致无法写入的问题；固定运行
  身份为 `473:473` 后，以上 App/Worker → syslog → Alloy → Loki 链路复验通过。
- production 外部 Alertmanager 配置的权限模型做了容器真实身份正向探针：运行文件
  为 `65534:65534`、`0400`，并由官方镜像实际用户成功读取、通过 `amtool` 校验。

本地 sink 只证明 Prometheus → Alertmanager → webhook 的合成链路，不是短信、邮件、
PagerDuty 或企业 IM 的 production 触达证明。
