## 1. 【高】全局 MQ 运维接口跨团队越权

**现象（实测）**

```text
探针账号 team=6，角色=OWNER（注册即成为自己团队的 OWNER）
GET  /api/v1/admin/mq/stats            → 200
POST /api/v1/admin/mq/replay-dlq?max=1 → 200 {"replayed":0}
```

**代码位置**：`product/web/MqAdminController.java:80`

```java
// admin 接口无团队上下文，角色直接取 JWT 的 role claim
private void requireOwner(Jwt jwt) {
    if (!"OWNER".equals(jwt.getClaim("role"))) { throw ... FORBIDDEN; }
}
```

**为什么是真问题**

- 只判断"是不是某个团队的 OWNER"，**不判断是哪个团队**；
- 任何人注册即成为自己团队的 OWNER，于是人人都拿到运维权限；
- DLQ 是 vhost 内**单一全局队列**，`replay-dlq` 会把**所有团队**的死信重新投回主交换机 ——
  这是跨租户的副作用，不只是"看到一点信息"；
- 与红线第 6 条「所有资源查询必须校验调用者的团队归属」直接冲突。

**建议（三选一，需所有者定夺）**

1. 引入与团队解耦的**平台级 admin 角色**（如 JWT 里 `platformRole=OPERATOR`），团队 OWNER 不再自动拥有；
2. 或把 DLQ 按团队拆分（队列名带 team 维度），重放按团队作用域执行；
3. MVP 阶段若接受单租户部署，至少要在 README 与部署文档明确写出该限制。

## 2. 【中】内部回写密钥有源码内默认值，应用层无 fail-closed

**代码位置**

```java
// WorkerProperties.java
@DefaultValue("frameflow-dev-worker-key") String resultKey

// application.yml
result-key: ${FRAMEFLOW_WORKER_KEY:frameflow-dev-worker-key}
```

**风险**：这个默认值写在公开源码里。若部署时漏配 `FRAMEFLOW_WORKER_KEY`，
任何人可持 `X-Worker-Key: frameflow-dev-worker-key` 向 `/api/v1/internal/analysis-results`
**伪造质检结论**（例如把候选改写成 `AUTO_REJECT` 或 `ANALYZED`）——
等于可以篡改整个质检系统的判定。

**已有缓解（但只在部署前）**

- `infra/scripts/remote-compose.yml` 用 `${FRAMEFLOW_WORKER_KEY:?required}`（缺失即启动失败）；
- `check-env-isolation.sh` 会拒绝 <24 字符或含 `change_me` / `example` / `local_only` 的值，并禁止密钥复用；
- 该脚本已接入 `promote-release.sh`、`request-certificate.sh`，CI 也有 `deploy-config` 作业。

**缺口**：以上都是**部署前脚本**。应用层本身不拒绝默认值 —— 绕过 `promote-release.sh`
直接起容器就会失守。

**建议**：应用启动时校验密钥非空、长度足够且不等于默认值，否则 fail-fast 拒绝启动。

**本次实测**（本地已配真密钥，行为正确）：

```text
X-Worker-Key: frameflow-dev-worker-key → 401
X-Worker-Key: 随机值                    → 401
```

## 3. 【中】内部接口密钥比较非恒定时间

`InternalAuthFilter:48` 使用 `key.equals(props.resultKey())`。
建议改为 `MessageDigest.isEqual(...)` 做恒定时间比较。
256bit 随机密钥在网络条件下实际风险很低，属标准加固项。

## 4. 【中】`GET /api/v1/batches` 恒返回 500，且 README 写错了

**实测**（demo 账号同样 500，与权限无关）：

```text
GET /api/v1/batches                            → 500 INTERNAL_ERROR
GET /api/v1/batches?page=0&size=50             → 500 INTERNAL_ERROR
GET /api/v1/batches?projectId=1                → 500 INTERNAL_ERROR
```

**根因**：`BatchController` 只有 `@PostMapping`（创建），**没有任何集合级 `@GetMapping`**。
运行时 springdoc 输出也证实该路径只有 `post` 方法。

**两个独立问题**

1. **README API 概览写的是 `GET|POST /batches`** —— GET 根本不存在，属文档错误；
2. 未映射路径返回 **500 而不是 405/404** —— 错误处理把这类情况兜底成了
   `INTERNAL_ERROR`，会掩盖真实问题（运维看到 500 会去查服务而不是查路径）。

**影响有限的原因**：前端不走这个接口，走的是 `/projects/{id}/batches`（已实测正常）。

**为什么测试没抓到**：`ContractConsistencyTest` 比对的是「手写契约 yaml ↔ springdoc 生成的文档」，
**不覆盖 README**。本例中契约文件本身只声明了 `post`，与运行时一致，所以测试正确地通过了 ——
问题是 README 没有测试守护。

## 5. 【低】邀请令牌明文入库

`team_invitations.token` 以明文存储（`InvitationRow`），且 `listInvites` 会把它返回给 OWNER。
对比之下 refresh token 是存 `sha256` 的，两处强度不一致。
数据库一旦泄露，未使用的邀请令牌可直接用于入团。

建议：与 refresh token 对齐，只存哈希，**仅在创建响应里返回一次明文**；
列表接口不再返回令牌（改为返回是否已接受 / 是否过期）。
