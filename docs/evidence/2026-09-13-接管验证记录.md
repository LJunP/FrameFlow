## 4. Web 生产构建：先失败后定位到宿主注入（已关闭）

`npm --prefix frameflow-web run build` 连续三次失败，错误栈全部落在宿主工具链内：

```text
Error: EEXIST: file already exists, mkdir '.../frameflow-web/.next/server/pages'
（前序 ENOENT ... mkdir .next/cache/webpack/server-production）
```

排查过程与结论：

1. 清空 `.next` 后重试 → 同样失败，排除"残留产物"；
2. 禁用沙箱重试 → 同样失败，排除"沙箱策略"；
3. 查环境变量发现 `NODE_OPTIONS=--require ".../shim/node-language-shim.cjs"`，
   即文件系统代理由该注入带入，与沙箱开关无关；
4. 剥离注入后构建**成功**：

```bash
cd frameflow-web
env -u NODE_OPTIONS <真实 node 绝对路径> node_modules/next/dist/bin/next build
```

产出 10/10 静态页，路由清单包含 `/`、`/login`、`/workspace`、`/projects/[id]`、
`/batches/[id]`、`/candidates/[id]`、`/selections/[id]`、`/team`、`/account`、
`/invite/accept` 与三个 API route；First Load JS 共享 103 kB。

结论：**宿主注入的 fs shim 无法承载 Next.js 构建的并发 mkdir，与项目代码无关**。
在普通终端执行 `npm --prefix frameflow-web run build` 即可正常通过。

## 5. 环境与操作要点（避免重复踩坑）

- 当前为**宿主机后端模式**：Java 在 `127.0.0.1:18080`，PG/Redis/Rabbit/MinIO/Worker 在 Docker。
- **前端实际在 3100，不在 3000** —— 3000 被本机另一项目的 Grafana 占用；

- Worker 容器 `FRAMEFLOW_API_BASE=http://host.docker.internal:18080`。
  若改为整栈 Compose，需改回默认 `app:18080`。
- 分页参数是 **0-based `page` + `size`**（不是 `pageSize`）；用错表现为 `total=1, items=[]`。
- 表名是 `generation_batches`，不是 `batches`。

  极易误判「服务没起来」（本次踩过一次）。

## 7. 阅读中发现的一处待确认点（本轮只记录，未改代码）

`UploadService.verifyAndFinalize()` 的两个 INVALID 分支处理不对称：

- 媒体签名不匹配分支：`markInvalid(...)` **后调用了** `progressCache.evict(batchId)`；
- 大小不匹配分支：`markInvalid(...)` 后**没有**失效进度缓存。

影响：候选因大小不符被判 INVALID 后，批次进度缓存最长会脏一个 TTL（30s），
期间 `/batches/{id}/progress` 与 SSE 可能仍返回旧的候选状态计数；不丢数据，
30 秒后自愈。判断为小瑕疵而非功能缺陷。
