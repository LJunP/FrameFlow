# 错误模型

## 1. 外部响应

```json
{
  "code": "PROJECT_NOT_FOUND",
  "message": "项目不存在或无权访问",
  "requestId": "...",
  "traceId": "..."
}
```

`traceId` 在不可观测的最小运行模式可以省略；`requestId` 必须存在。不得返回服务名、数据库错误、堆栈、Token 或内部路径。

## 2. HTTP 映射

| HTTP | 用途 | 是否默认重试 |
|---:|---|---|
| 400 | 参数校验失败 | 否 |
| 401 | 未认证或 Token 无效 | 否 |
| 403 | 无权限 | 否 |
| 404 | 资源不存在或按安全策略隐藏 | 否 |
| 409 | 乐观锁冲突、重复或非法状态 | 否，客户端需重新读取 |
| 429 | 限流 | 仅按 `Retry-After` 和业务幂等性决定 |
| 500 | 未预期错误 | 不向客户端承诺重试 |
| 502 | Gateway 到下游响应无效 | 由调用方按幂等性决定 |
| 503 | 依赖不可用、熔断或受控降级 | 由预算和幂等性决定 |
| 504 | 下游超时 | 由预算和幂等性决定 |

## 3. 下游错误映射规则

- 下游 4xx 通常透传稳定业务错误码，不重试。
- 下游超时、连接失败和部分 5xx 由 Resilience4j 处理；熔断打开时返回受控 `DEPENDENCY_UNAVAILABLE`。
- 降级不能伪造写入成功；写操作应返回可查询的待处理任务或明确失败。
- Gateway 不把内部异常原因暴露给客户端，但日志和 Trace 必须保留关联信息。
- 异步任务失败通过任务状态、错误分类和重试/DLQ 查询，不用 500 表示后台最终结果。

## 4. 错误码要求

错误码稳定、可搜索、与具体服务实现解耦。错误记录至少包含：`code`、`message`、`requestId`、`traceId`、时间和必要的脱敏业务标识。
