## 2. 产品本质

### 2.1 标准定义

FrameFlow Select 是一个面向 AI 生成短视频生产团队的**批量质量门禁与候选优选系统**。

系统接收：

```text
项目目标 / Prompt / Brief / 品牌要求 / 平台规格
+
一批 AI 生成短视频候选
```

系统输出：

```text
技术不合格候选
+
存在 AI 生成瑕疵或业务不一致的候选
+
需要人工复核的候选
+
去重后的短名单与 Top-K 排名
+
时间码、关键帧、规则和置信度证据
```

### 2.2 价值公式

```text
FrameFlow Select 价值
=
减少的人工完整观看量
×
被正确保留的优质候选比例
×
问题证据的可操作性
-
分析成本
-
误淘汰损失
```

系统首要任务不是“给视频打分”，而是：

> 在不显著漏掉优质候选的前提下，尽可能减少用户必须完整观看的视频数量。

### 2.3 所处位置

```text
视频生成模型 / 生成平台
        ↓
生成几十至几百个候选
        ↓
FrameFlow Select
技术检查 → 瑕疵检测 → Brief 对齐 → 去重 → 排名 → 人工复核
        ↓
短名单 / 修改建议 / 发布准备
        ↓
剪辑、投放或发布系统
```

FrameFlow Select 不替代视频生成工具，也不替代最终人类创意判断。

## 3. 首个市场切口

### 3.1 首要用户

首个验证对象锁定为：

> **批量生成 5～60 秒电商短视频或商品广告素材的小型 AI 内容团队。**

典型特征：

- 2～20 人；
- 每批次至少 20 个候选，常见为 50～300 个；
- 同一商品、同一营销目标或同一 Prompt 生成多个版本；
- 需要人工筛选明显瑕疵、规格错误、商品展示不足和重复内容；
- 结果进入人工剪辑、投放测试或客户确认；
- 对“节省审核时间”和“避免错过好素材”有直接价值。

### 3.2 首个产品模板

MVP 只保证一个可用的质量模板：

```text
ECOMMERCE_SHORT_AD_V1
```

模板覆盖：

- 5～60 秒短视频；
- 9:16 为主，兼容 1:1 与 16:9 的显式配置；
- 商品可见性；
- 开场 Hook 或商品首现时间；
- 指定文案、卖点、CTA；
- Logo、颜色和禁止内容；
- 技术规格；
- 生成瑕疵、时序一致性和重复候选；
- Top-K 优选。

### 3.3 后续可扩展对象

只有首个模板通过真实试点后，才允许扩展：

```text
AI 数字人口播
AI 短剧片段
品牌社媒内容
游戏宣传素材
通用创意短视频
生成平台 API 质检
```

扩展用户不等于改变产品本质；仍必须围绕“批量筛选与优选”。

## 4. 产品北极星与护栏指标

### 4.1 北极星指标

**人工完整观看减少率（Full-watch Reduction Rate，FRR）**

```text
FRR = 1 - 需要人工完整观看的候选数 / 输入候选总数
```

FRR 不能单独使用，必须同时满足优质候选保留护栏。

### 4.2 第一护栏

**优质候选保留率（Good Candidate Retention，GCR）**

```text
GCR = 被系统保留的人类高质量候选数 / 人类高质量候选总数
```

项目优化优先级：

```text
先保护 GCR
再提高 FRR
最后优化成本和速度
```

### 4.3 关键质量指标

- 严重问题召回率；
- 误淘汰率；
- Top-K 优质候选召回率；
- NDCG@K / 人工排序一致性；
- 问题建议人工确认率；
- 时间码定位误差；
- 分析成功率与部分失败率；
- 每分钟视频分析成本；
- 每批次端到端延迟；
- 人工推翻自动判断的比例。

### 4.4 产品验证目标

初始门禁目标写入 BOOK-05。阈值可以根据真实标注数据修订，但必须遵守：

1. 不能在看到当前结果后临时降低阈值以宣布通过；
2. 阈值调整必须说明数据集、基线、误差和业务影响；
3. 误淘汰率的优先级高于单纯提升自动淘汰数量；
4. 任何自动淘汰规则都必须在独立保留集上验证。

## 5. 产品不变量

以下规则在 MVP 和早期试点期间固定：

1. **批次是产品核心对象。** 单条视频分析只是批次能力的组成部分。
2. **质量是向量，不是一个神秘总分。** 总分只能用于排序，不得掩盖具体问题。
3. **门禁与排名分离。** 硬性违规决定是否进入候选池，软性质量决定候选池内排序。
4. **所有可操作结论必须有证据。** 最低证据为规则、时间范围和可查看的媒体片段或关键帧。
5. **视频文件和分析结果不可被原地覆盖。** 重传、重跑和重排都形成新版本或新快照。
6. **AI 不自行宣布成功。** 任务状态、规则判断、测试与人工复核由确定性控制面管理。
7. **高价值误淘汰比多看一条差视频更危险。** 默认策略偏保守。
8. **分析失败不得伪装成质量不合格。** 失败进入 `ANALYSIS_ERROR` 或 `REVIEW_REQUIRED`。
9. **模型和 Prompt 可替换。** 业务记录必须固定所用版本，不能依赖某一家 Provider 的内部字段。
10. **人类反馈是产品数据，不覆盖机器原始结果。** 两者分别保存，用于校准和评测。

## 7. 产品原则

### 7.1 证据优先

每个 Finding 必须明确：

```text
发现了什么
违反了哪条规则
发生在什么时间
依据是什么
置信度是多少
系统建议怎么处理
```

### 7.2 级联检测

优先使用便宜、稳定、可解释的方法：

```text
元数据与规则
→ FFmpeg/OpenCV
→ 专用模型
→ 多模态大模型
→ 人工复核
```

禁止所有候选一开始就使用最贵模型完整观看。

### 7.3 有界智能

产品运行时使用确定性 DAG 和有限 AI 节点：

- 不允许无限 ReAct 循环；
- 每个 AI 节点有最大调用次数；
- 输出必须通过 JSON Schema；
- 不允许模型递归创建新的 Agent；
- 不允许模型修改质量规则、阈值或自身权限；
- 失败必须终止或进入人工复核。

### 7.4 先可测，再自动化

如果一个“质量维度”无法定义标注方法、指标和失败样例，则不能进入自动淘汰逻辑，只能作为实验性提示。

### 7.5 先单体，再拆分

Java 采用模块化单体，Python 采用一个可插拔 Worker。只有出现独立扩缩容、故障隔离和团队边界证据时才拆分，不为简历制造服务数量。

## 8. 成功、调整与停止条件

### 8.1 可行性成功

可行性阶段至少证明：

- 存在三类以上用户认为有价值、可自动定位的问题；
- 自动结果明显优于仅按文件规格或随机排序的基线；
- 关键问题能够给出用户可理解的证据；
- 单位分析成本与人工节省存在合理空间；
- 模型失败不会导致不可控错误淘汰。

### 8.2 MVP 成功

MVP 至少证明：

- 可处理完整批次；
- 能显著减少人工完整观看量；
- 优质候选保留率满足护栏；
- 用户能够理解并修改系统判断；
- 结果可以导出或进入下一工作环节；
- 失败、重试、取消和部分完成可控。

### 8.3 必须调整的信号

出现以下任一情况，不得继续堆功能：

- 两轮评测均不能优于简单基线；
- 用户主要需求不是筛选，而是生成或剪辑；
- 人工频繁推翻高置信度结论；
- Top-K 丢失优质候选超过护栏；
- 模型成本高于节省的人工价值；
- 用户不愿上传内容或无法接受 Provider 数据边界；
- 首批用户平均批次太小，人工筛选痛点不成立。

### 8.4 停止或换切口的条件

- 无法获得最少可用的评测样本和目标用户反馈；
- 连续两个独立模型/方法仍无法达到最低可用准确度；
- 目标用户的真实工作流不包含批量候选筛选；
- 产品只剩“调用模型返回一段评价”，没有可验证差异；
- SourceLens-AIOS 和 FrameFlow Select 的资源冲突导致两者都无法形成完整闭环。

停止某个方案不等于否定项目；可以保留“批量质量门禁”本质，调整首个垂直模板。

### 9.3 ADR 使用门槛

只有满足至少一个条件才创建 ADR：

- 预计影响两个以上阶段；
- 迁移成本明显高；
- 涉及数据不可逆、公开契约、安全或供应商锁定；

下列情况不创建 ADR：

- 普通库升级；
- 单个页面布局；
- 单个 Task 的实现细节；
- 可在一次提交内安全回滚的局部重构；
- 为了证明“治理完整”而写文档。

## 10. 变更分类与批准

### 10.1 L0：实现细节

例如局部类名、查询优化、UI 微调。由实现者决定，测试通过即可。

### 10.2 L1：契约变更

例如字段、API、事件、状态机局部变化。需要：

- 更新机器契约；
- 兼容性说明；
- 测试与迁移；
- Reviewer 批准。

### 10.3 L2：产品范围变化

例如新增一种自动淘汰规则、新角色、新目标模板。需要：

- 用户问题证据；
- 指标影响；
- 对 BOOK-02/03/04/05 的影响；
- 项目所有者批准。

### 10.4 L3：方向变化

例如转向视频生成、通用内容审核或通用 Agent 平台。需要：

- 替代方案比较；
- 当前方向失败证据；
- 已投入资产处理；
- 成功/停止标准；
- 项目所有者书面批准；
- 宪章主版本升级。

未完成 L3 流程，不得通过悄悄新增模块让项目事实发生漂移。

## 11. 功能准入测试

任何新功能进入产品 Backlog 前必须回答：

1. 它是否直接改善 FRR、GCR、问题可操作性、成本或可靠性？
2. 首要用户是否真实需要？证据是什么？
3. 能否在当前或下一阶段被验证？
4. 是否属于 FrameFlow Select，而不是 SourceLens-AIOS？
5. 是否存在更简单的规则、脚本或人工流程？
6. 它会不会扩大数据、权限、合规或运维责任？
7. 删除它是否仍能完成当前阶段核心闭环？

准入规则：

- 第 1～4 题任一无法明确回答，拒绝；
- 第 7 题回答“可以”且没有试点证据，延后；
- 仅因为“热门”“适合简历”“Agent 能做”不能成为理由。

## 12. 防偏航红线

### 12.1 产品偏航

每个 Stage Review 必须重新检查：

```text
本阶段是否让批量筛选更准确、更快或更可信？
```

如果答案是否定的，不能宣布产品进展。

### 12.2 技术偏航

以下技术没有触发证据时禁止进入主线：

```text
微服务
Kafka
Kubernetes
Istio
Elasticsearch
分布式锁
向量数据库集群
自研推理服务
```

### 12.3 Agent 自循环

- 同一任务最大返工次数由 BOOK-06 定义；
- Agent 不得批准自己的输出；
- Agent 不得修改验收标准来满足自己；
- 连续两次没有新增可验证信息时强制停止；
- 模型不得无限讨论或多 Agent 辩论。

### 12.4 过度治理

- 六本手册之外不新增“大而全”文档；
- 文档工作默认不超过单个迭代投入的 10%；
- 除产品转向阶段外，不允许纯文档里程碑；
- 代码、评测集和用户结果优先于格式完善；
- 已由机器契约表达的字段不在多份 Markdown 重复维护。

```text
Java 企业后端
+

+
AI 评测与数据闭环

Web 产品交付
```
